> **Owner's decision, 2026-10-09 (overrides design decision 1).** Sign-in is **Google only** for now:
> Google's button and One Tap, scopes `openid email profile`, no password ever. The emailed-link path
> is deferred: Tasks 3 (mail) and the magic-link parts of 4, 5 and 8 are not built, nothing needs a
> mail provider, and the contracts and limits below stay as the design for when it is. The Record at the
> end says what was built in their place.

**Goal:** A person can sign in with an emailed link or with Google, see and change their account, sign out everywhere, and delete the account, with the flag on; nothing changes for anyone who does not sign in.

**Architecture:** Better Auth runs inside `apps/api` on the same PostgreSQL pool, behind thin routes of ours (`/api/session`, `/api/account`) that call `auth.api` and carry every guard the scan route has (Origin, Turnstile, limits). The library's own HTTP surface is not exposed, except Google's callback. Emailed links open static pages of ours with the token after `#`; the page spends it on a click. Every request the API makes leaves through the egress proxy: `safeFetch` for Turnstile and mail, Node's env proxy for the library's calls to Google.

**Tech Stack:** `better-auth` 1.7.6 (exact, MIT), Hono 4.13.10, Drizzle 0.45.3 on `pg` 8.23.0, Zod ^4.6.5, Preact islands in Astro 7.3.5, Vitest ^5.0.1, Node ≥ 22.12 (CI 22 and 24).

**Spec:** `docs/design/phase-4.md` §1 (accounts), §6 (security and privacy), §7 (M4.1). Branch `phase-4/accounts`, from `main` once the design is merged; its own pull request.

## Global Constraints

- Free single-page tools stay free and signup-free (`CLAUDE.md`). A request without our session cookie takes today's path.
- No invented numbers in UI copy, READMEs, seed data, pricing or reports (`CLAUDE.md`). Numbers in copy come in as parameters from code constants, as `SCAN_FORM` does.
- Plans and quotas live in `packages/plans` and are enforced in the API. Abuse limits are read from the environment; production refuses to start without them, and development values are named `DEVELOPMENT_*`.
- Every request the API makes leaves through the egress proxy (M2.1 plan §5b). ESLint bans `fetch` and the network modules outside `@arablyzer/egress`; the site's `fetch` gets one named file (Task 10).
- Nothing is stored that BUILD-PLAN §14 does not allow: no IP address, User-Agent, OAuth token or profile picture in the account tables; no email address, token or link in a log (the log mailer, for development and the end-to-end stack, is the one place they are printed, and production refuses it).
- Ask first (`CLAUDE.md`): this milestone creates no key, account, domain or payment. Google and Resend are the owner's, by their approval.
- pnpm 10.32.1; exact versions for runtime dependencies; `pnpm install --frozen-lockfile` in CI; `pnpm audit --audit-level high` must pass.
- TypeScript ~6.0.3, strict, `erasableSyntaxOnly`, `verbatimModuleSyntax`. Prettier: no semicolons, single quotes, width 100, trailing commas.
- Every new Arabic string is `reviewed: false`; the `arabic-copy` job stays red until the owner reads it.
- Commits are `type(scope): subject`, and end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. A task ends with its package's `typecheck` and `pnpm exec eslint <files touched>` green; the whole `pnpm lint && pnpm format:check && pnpm typecheck` before the pull request.

## Review Focus

Each line names the input, what a reasonable person expects, and the task whose test pins it.

1. **A mail scanner opens the emailed link.** Nothing is signed in or deleted by a GET: the link is a page of ours, the token is after `#`, and the page makes no API request until the button is pressed. Tasks 3 and 11.
2. **The address is not one address.** `Ali@Example.com`, a leading space, `a@b.c\r\nBcc: x@y.z`, two addresses, 255 characters, an empty string: the first two are the same account and the same limit window; the rest are refused before Turnstile is asked or any mail is made. Task 5.
3. **The cookie is garbage.** Tampered, expired, revoked, from another deployment, or the store is down: `401` (or `503` for the store), never `500`, and never a scan refused. Task 5.
4. **One link, two clicks at once.** Exactly one session; the other click says the link is used, not a server error. Tasks 5 (memory) and 8 (PostgreSQL, where atomicity is real).
5. **Google's identity is odd.** An unverified address, none at all, the same address as a magic-link account in another case, a replayed or tampered state: no session unless the address is verified; one user for one address. Task 6.

## 2. Contracts

**Routes** (`packages/api-contract`; JSON; every answer `Cache-Control: no-store`; with accounts off, all `404 {"error":"not-found"}`):

| Route | Guards, in order | Success | Refusals |
|---|---|---|---|
| `POST /api/session/link` `{email, turnstileToken, lang}` | Origin + JSON + 8 KB + schema; `signIn` per visitor; Turnstile (`signin`); `email` per address (a limited one still answers 200, and sends nothing); `mail` cap | 200 `{status:'sent'}` | 400 `bad-request`, 429 `rate-limited`, 403 `turnstile-failed`, 503 `unavailable` |
| `POST /api/session` `{token}` | Origin + JSON; `signIn` per visitor | 200 `AccountSummary` + cookie | 400 `invalid-token`, 429 |
| `POST /api/session/google` `{lang}` | Origin + JSON; `signIn` per visitor | 200 `{url}` + state cookie | 400, 404 (not configured), 429 |
| `DELETE /api/session` | Origin | 204, cookie cleared (also with no session) | |
| `DELETE /api/sessions` | Origin, session | 204 | 401 |
| `GET /api/account` | session | 200 `AccountSummary` | 401 `unauthorized`, 503 |
| `PATCH /api/account` `{language}` | Origin + JSON, session | 200 | 400, 401 |
| `POST /api/account/deletion` | Origin, session, `signIn` per visitor | 202, one mail | 401, 429, 503 |
| `DELETE /api/account` `{token}` | Origin + JSON, session | 204, cookie cleared | 400 `invalid-token`, 401 |
| `GET /api/auth/callback/google` | the library's own | 302 to the account page of the language asked for | 302 to that language's `/login/?error=…` |
| anything else under `/api/auth/*` | none | | 404 |

`AccountSummary = { id, email, name, language: 'ar' | 'en' | null, createdAt }`. `language` is null until the account page first sets it from the page's language, so both sign-in methods take the same path and no heuristic guesses it.

## Acceptance criteria

1. With `ARABLYZER_ACCOUNTS=on`: a person signs in by an emailed link (and by Google, against a stub in CI), signs out, signs in again, asks to delete the account, confirms by the emailed link, and no table on PostgreSQL holds their id or address afterwards. With it off, every account route answers 404.
2. Anonymous scans, tool scans, events, reports and report deletion behave as before with the flag on and off: the earlier tests pass unchanged, and a test shows no `Set-Cookie` and no account-table read. The home page and the tool pages load no account script.
3. No account row holds an IP address, a User-Agent, an OAuth token or a picture; verification identifiers are hashed; in the production configuration no log line holds an address, token or link.
4. Turnstile, the per-visitor, per-address and mail limits refuse as the routes table says; production refuses to start with accounts on and any setting missing.
5. Every request the API makes leaves through the egress proxy: Turnstile and mail through `safeFetch`, and Google's token exchange through Node's env proxy, shown on Node 22 and 24 and in Smokescreen's log.
6. The worker's database role reads `scans` and nothing else.
7. The five Review Focus lines each have a passing test.
8. `pnpm lint`, `format:check`, `typecheck`, `test:unit`, `test:ssrf`, `test:services`, `test:browser`, `site:audit`, `seo:audit` and `test:stack` pass; Lighthouse's gate on the indexable pages is unmoved.
