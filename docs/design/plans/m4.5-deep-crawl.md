# M4.5 Deep Crawl with Template Grouping — Implementation Plan

> **ملخص للمالك:** المعلم الخامس من المرحلة 4 (والدفع M4.4 يأتي آخراً بقرارك): من سجّل الدخول يضغط «زحف عميق» على موقع محفوظ، فيجد Arablyzer صفحات الموقع (من خرائط الموقع أولاً ثم الروابط الداخلية) بأدب (يحترم robots.txt و`Crawl-delay` وبوتيرة هادئة) حتى سقف الخطة (المجانية: 50 صفحة). ثم **يجمع الصفحات في قوالب** (صفحة منتج، مقال، تصنيف…) بحسب شكل الرابط وهيكل الصفحة، ويفحص كل صفحة فحص HTML سريعاً، ويفتح **صفحة ممثِّلة واحدة من كل قالب** في المتصفحات الثلاثة. التقرير يقول «هذه المشكلة في 38 من 40 صفحة من قالب المنتج» مع أمثلة. لا شيء يظهر للزائر المجهول، ومطفأ مع `ARABLYZER_ACCOUNTS`. **المطلوب منك:** نصوص الواجهة العربية (`reviewed: false`) ورقم السقف إن أردت غير 50.

**Goal:** A signed-in person crawls a saved site: the pages are found, grouped into templates, every page gets the HTML checks, one representative per template gets the full three-browser scan, and the report says which issue sits on how many pages of which template.

Design source: `docs/design/phase-4.md` (the crawl was left to phase 5 there; the owner moved it up, and payments, M4.4, come last by his decision). Built on `m4.2-sites.md` (saved sites, account scans) and `m4.3-monitoring.md` (the second API-image process, the lease, the scan start without a visitor).

## 0. Measured before planning (2026-10-09)

| Question | Result |
|---|---|
| Is there a crawl to reuse? | No. `packages/seo` `audit/` is the owner's own-site audit of built pages (no network). The engine reads sitemaps only to judge them: `readSitemap` counts entries and keeps no addresses, and `fetchSitemaps` reads at most three files and no index children. `siteLinks(page)` (the page's links to its own origin, fragment-free, deduplicated) is reusable as it is. |
| robots.txt | The scan treats a page the visitor asked for as a visit: only a group that names ArablyzerBot opts it out. A crawler is held to `User-agent: *` too (RFC 9309), and to `Crawl-delay`, which `parseRobotsTxt` does not read. `matchRobots` / `robotsMatcher` already do the `*` fallback and the longest-match rules; the crawl uses them. |
| Where pages are fetched | Fetching and parsing a site's HTML belongs where a scan's does: the scanner container, on the egress-only network, parsing in a thread of its own. The API image never parses a page. The crawler (API image, like the monitor scheduler) asks the scanner, over the worker's token, for facts. |
| HTML-only checks | `evaluatePage(page, {ruleIds})` runs rules on facts already collected, with no network. The rules whose `needs` are within `http, headers, html, text, response` are the "light" set (no robots, links, DNS, CrUX, render). One fetch gives links, skeleton and issues: no second request to the site. |
| DOM skeleton | `HtmlFacts` has no tree. `DocumentIndex` (one linear pass, document order) is where it can be read without a second parse: the set of paths of structural elements (`main>section>ul`), repeats not counted. |
| Starting a representative's scan | `monitor/scheduler.ts` `launch` is the pattern: the account's place, DNS vetting, the host bucket, the queue's lower half, store → link → event → queue. The crawl does the same with `source = 'crawl'`. |
| Provision | `crawl_pages.seq` is a serial: the application role needs `USAGE` on sequences that existing migrations made (default privileges reach only later ones). One line in the grants. |

## Global Constraints

- Invisible and 404 with `ARABLYZER_ACCOUNTS` off; the crawler process idles with it off. Anonymous scans, tools and reports unchanged (the anonymous-path tests run unchanged).
- **Polite and bounded.** Same origin only (after the start page's redirects; a redirect off the origin ends the fetch there). robots.txt before any page, `*` groups counted, a file that cannot be read keeps the crawler out (RFC 9309). `Crawl-delay` is honoured up to 10 s; the pause between two pages is `max(ARABLYZER_CRAWL_DELAY_MS, Crawl-delay)` (default 1000 ms); one page at a time per crawl. Links and sitemap addresses are capped, query variants of one path are capped (a calendar is not a crawl), file types that are not pages are skipped.
- **One crawl at a time per account**, held by the database (partial unique index on active crawls), not by the route. Cancellable: a queued crawl at once, a running one at its next page.
- **The plan's cap** is `crawlPages` (`ARABLYZER_PLAN_ACCOUNT_CRAWL_PAGES`, default 50 for the free plan, in production too; paid plans read the same name with their prefix). Pages asked for count, answered or not; pages robots.txt keeps out do not.
- **Template-aware sampling.** The next page is taken from the kind of page (a rough address shape) with the fewest pages asked for, so a 5,000-page sitemap in which the products come first still visits articles and categories.
- **Browsers only for representatives.** At most `ARABLYZER_CRAWL_REPRESENTATIVES` per template (default 1) for at most `ARABLYZER_CRAWL_RENDERED_TEMPLATES` templates (default 10), largest first, each through the scan queue's lower half, the account's `inFlight` place and the host bucket, like a monitor's scan.
- Everything fetched is untrusted: the scanner's answers are checked against Zod schemas with caps; titles and addresses reach the page as text; rule titles come from the engine.
- No new personal data. Crawl rows go with the account (cascade; erasure test searches every table) and with the site; they are kept as long as the plan's history days (swept by the crawler process, whose role can see accounts); representatives' scans are ordinary linked scans and follow the existing sweep.
- UI on the R7 scale (`card p-card rounded-card`, `heading-2/3`, `text-body/small/meta`, `chip`, `btn-grad`/`btn-white`, 44 px targets, logical `text-start/end`, no `style=` (CSP), no letter-spacing on Arabic). Every new Arabic string is `reviewed: false`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **robots.txt**: a disallowed page is never asked for; an unreadable file means nothing is crawled; `*` counts; the sitemap addresses are filtered through it. Task 2.
2. **Same origin**: a redirect to another origin ends the fetch, a link to another host is never added, the start page may move to `www`/https once. Task 2.
3. **One at a time**: many starts at once store one; a second crawler cannot take a crawl whose lease is held; a dead crawler's crawl is resumed from its stored frontier. Tasks 4, 6.
4. **Grouping is deterministic and explainable**: the same pages give the same templates and keys; a template is named from its address; leftovers are "standalone pages", not a guess. Task 5.
5. **Erasure and retention** leave nothing in the new tables. Task 4.
6. **The scanner stays a scanner**: reading a page needs no browser, so it neither waits for a scan nor retires the process; at most two reads at once; the worker's token is the only way in. Task 3.

**Settings:** `ARABLYZER_PLAN_ACCOUNT_CRAWL_PAGES` (50), `ARABLYZER_CRAWL_DELAY_MS` (1000), `ARABLYZER_CRAWL_REPRESENTATIVES` (1), `ARABLYZER_CRAWL_RENDERED_TEMPLATES` (10); the crawler process also reads `ARABLYZER_SCANNER_URL` and `ARABLYZER_SCANNER_TOKEN` (as the worker does).

**Templates.** Pattern per address: segments classified (numbers, ids, dates, long or non-ASCII slugs become `:num`, `:id`, `:date`, `:slug`); then a trie over all addresses where a node with five or more children, mostly leaves, collapses them to `:slug`. Home is its own template; patterns with fewer than two pages go to "standalone pages". Within a pattern, pages are clustered by skeleton similarity (≥ 0.8 Jaccard against the cluster's first page; small clusters fold into the largest). Name = kind (from words in the address: product(s), shop, item, p → product; blog, news, article(s), post(s) → article; category, collections, tag, c → category; help, faq, support → help; Arabic equivalents) + the pattern. Representative = the shallowest page with the dominant skeleton.

## Tasks

1. **Plan numbers and contract** — `crawlPages`, shapes, `conflict`.
2. **Collectors and engine** — skeleton, sitemap addresses, `createCrawler`; tests on fixture sites (robots, sitemap index, pages).
3. **Scanner** — protocol, `remoteCrawler`, route with its own concurrency cap, `localCrawler` for dev.
4. **Store** — tables, migration, `CrawlData` over one contract suite (memory and PostgreSQL), grants, erasure.
5. **Grouping and the report** — pure: `bucketOf`, `normalize`, `groupTemplates`, `buildReport`; unit tests.
6. **The crawler** — claim with lease, bootstrap (start page, sitemaps), the page loop with pacing and cancel, grouping, representatives through the scan queue, ingesting their reports, retention; fake clock/scanner tests.
7. **Routes and process** — the six routes, `main.ts`, dev wiring, config.
8. **The page** — launch from a saved site's card, progress, report: summary, templates, issue-by-template table, per-page drill-down; AR + EN copy.
9. **Infra, CI, the record.**

## Acceptance criteria

1. Flag on: a crawl of a fixture site with a sitemap and robots.txt finds its pages, never asks for a disallowed one, stays on the origin, stops at the cap, groups products/articles/categories into three templates, runs the HTML checks on every page and the full scan on one representative per template, and reports "N of M pages" per template with examples. A second start while one is active is `409`; cancelling stops it; erasing the account leaves nothing.
2. Flag off: every route 404 and the crawler idles; anonymous scans, tools and reports unchanged.
3. `pnpm lint`, `format:check`, `typecheck`, unit and service tests, web build, `site:audit` pass.
