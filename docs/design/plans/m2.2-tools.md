# Arablyzer — M2.2: the tool pages

> The second milestone of Phase 2 (`docs/design/phase-2.md` §5): the tool page template and the directory, then the
> tools the existing rules can run. BUILD-PLAN §5.1 (the toolbox), §6.1 (the tool page template), §6.5 (technical
> SEO). The owner asked on 2026-09-29 for every phase to be built without stopping for approvals, and to keep the
> design as it is, open to a whole redesign later: this plan is written as the work goes, not before it.

Two pull requests, as M2.1 was four:

- **M2.2a** — a tool runs its own rules end to end, the template in the Lab design, the directory, the three tools
  there are.
- **M2.2b** — the tools the 47 rules can run, each with its copy in both languages and its live example tested.

---

## 1. Design (M2.2a)

**A tool's scan.** A tool page asks for a scan with its tool's slug (`POST /api/scans {url, turnstileToken, tool}`).
The API checks the slug against the tools' registry (`@arablyzer/tools/registry`: each tool's slug, category and
rules, without its page's copy), records it with the scan (a `tool` column, migration 0001) and queues it; the
worker passes it to the scanner, which runs the tool's rules alone. A browser opens only when one of them reads the
rendered page, and there are no lab metrics: a tool that reads the HTML answers in a few seconds. The scan's summary
names its tool; the report is the same report, of those rules.

**The page** follows BUILD-PLAN §6.1 in its order, in the approved Tool-WhatsApp and Tools boards: the heading and
its line; the tool before any section (the address, Turnstile, the result under the form as the scan runs); what it
checks; a wrong and a right example; how to fix; questions answered in the page (headings, not collapsed: the audit
reads them, and so do answer engines); what the tool runs and the tools near it; the methodology and the date of
the last update. The site's self-audit holds every built tool page to the whole template.

**The directory** lists the categories of §5.1 that have tools, with their colours and numbers, the Arabic layer
apart, a card per tool (its line, and what it reads: HTML, robots.txt, three browsers, Chrome's data) and a search
over the cards. The home page gets its tools section (§ 04 in the design).

**A tool's result** has its own link, the scan's report page, which says it is a tool's result, names the tool, and
shows no overall score: the score is the whole scan's.

**Build.** The tools' copy is Markdown that Astro's build cannot read, as the rules' is: `scripts/generate.ts`
renders it into `src/generated/tools.json`, each example highlighted as the design draws it.

**CI.** Every tool page is one template, and there will be dozens: Lighthouse measures the pages that stand for the
rest (every page but the reports and the tool pages past the first in each language), in a job of its own; the
site's self-scan scans every page, those pages in three engines and the other tool pages in Chromium.

## 2. Record (M2.2a)

**Built:** the tool scan through the API, the queue, the worker and the scanner; `/tools` and `/tools/<slug>` in both
languages; the directory and its search; the home page's tools section and "Tools" in the header; a tool's result on
the report page; each tool's card line (`summary`); the audit of built tool pages; Lighthouse in its own job.

**Checked (2026-09-29, the owner's Mac):**

- The site's self-audit: 12 pages, no problems; a tool page with its FAQ section renamed fails it (`missing <section
  id="faq">`).
- The site scanning itself, Chromium and Firefox (WebKit in CI): all 10 indexable pages pass every rule; the report
  page as a tool's result passes too.
- Through the whole stack in a browser: the RTL checker on golden site 04 showed "the page passes this check" under
  the form in a few seconds, with its two rules, and its link opened the report page as the tool's result; no
  console error.
- The stack's test, 20 tests: the tool pages served at their clean addresses, and a tool's scan with the tool's two
  rules and no browser.

**What running it found:** the worker read a queued job's id and url alone, so a tool's scan ran as a whole scan
(every rule, three browsers): it reads the job through `scanJobOf` now, tested. A whole scan running in three
browsers on the owner's Mac once slowed the API's Turnstile check past its 5 s; it did not recur, and the server has
twice the processors (§18.3.1).

**Left for later:** the rule pages the tool pages will link to (M2.4); the site's 404 page; a "report a wrong result"
link once the repository is public.

**The independent review (2026-09-29)** ran the stack and found two blockers, both fixed and tested:

- **A tool's result said the page passes when the check could not run** (a rule in error, a partial or failed scan).
  The headline is a pure function now, tested with partial, failed and errored reports: a green check only for a rule
  that passed, "incomplete" with the scan's notices otherwise. The report page says "no problems" only when every rule
  ran.
- **A tool's scan sent the page's URL to the Chrome UX Report though none of its rules reads it.** The scanner drops
  the CrUX key for such a tool, and the engine asks CrUX only when a rule it runs needs it; tests count zero queries.

And fixed with them: Arabic rule titles in their own direction; one short live announcement instead of the whole
result read aloud; a tool page's script cut from 30.4 KB to 25.0 KB gzip (the tool's own strings, the evidence apart
from the report page); bidi controls in a hostile page's evidence shown by name, not obeyed; the directory's search
folding Arabic spellings (أ إ آ, ة ه, ى ي, tatweel, harakat, «ال»); the site's sections on a phone and in the footer;
no whole-scan score stored for a tool's scan; one address per page, the others redirected for good (308); the
self-audit holding a tool page to every part of its template, the island's tool included; a browser test of a tool page
in three engines, with real two-rule reports.

## 3. Record (M2.2b)

**Built:** 27 tools on the rules there are, 30 in all, each with its page in both languages: crawling and indexing
(robots.txt, indexability, canonical), the page (title and description, the H1, link previews), structured data,
languages (hreflang, the page's language), speed (image weight), commerce (the product page, Gulf prices), trust
(accessibility, mixed content), and the Arabic layer (letter joins, Arabic fonts, font fallback, letter spacing,
numbers and English in Arabic text, mirrored icons, logical CSS, horizontal overflow, punctuation, digits, tatweel, the
form test, phone fields). Four writers drafted the copy, each tool from its rules' code and copy; the Arabic of every
new tool waits for the owner (`reviewed: false`).

**The examples are checked as the copy is written.** `test/example-check.ts` holds the check the test runs and
`scripts/check-copy.ts <slugs>` prints it for a tool, with the copy's structure: a tool that reads the HTML or robots.txt
runs its rules on its examples (the wrong one fails, the right one passes every rule it speaks to); a tool that renders
the page shows excerpts of its rules' fixtures, which the engine's browser suite renders in three engines.

**What checking found:**

- **A page about a problem shows the problem.** The site's own rules failed tool pages that quote what they flag in
  their prose: a stretched word on the tatweel checker's neighbours, Eastern Arabic digits, a price with two decimals.
  The rules leave text in code alone, which is where a quoted sample belongs: the copy writes them in backticks.
- **The self-scan caught what the HTML audit cannot.** The numbers-and-English checker's description said «C++» in
  Arabic text, which every browser draws as «++C»: the very fault the tool finds, flagged by its own rule in Chromium.
  The description names no such word now.

**Checked (2026-09-29, the owner's Mac):** the tools' tests (every example in both languages), the site's self-audit
(66 pages), the site scanning itself in Chromium and Firefox (every page, every rule), unit tests, lint, types and
formatting.
