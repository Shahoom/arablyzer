**Goal:** A signed-in person saves sites, scans them with one click, and sees their recent scans with scores and report links; their scans have their own quota and skip Turnstile; nothing changes for anyone who does not sign in.

Design source: `docs/design/phase-4.md` §1.3, §2.1–2.4, §6. Built on `m4.1-accounts.md` (Google-only sign-in).

## 0. Measured before planning (2026-10-09)

| Question | Result |
|---|---|
| Where a visitor's limits are taken | `POST /api/scans` (apps/api/src/app.ts): `attempt:<visitor>` bucket, Turnstile, `connection:<visitor>` bucket, `network:` bucket, `holdPlace(visitor)`, DNS, `perHost` bucket, queue length. Account scans replace the Turnstile step and the two visitor keys with the account's; the attempt counter, network bucket, per-host bucket and queue cap are kept |
| Reading the session | `readSession` lives inside `mountAccounts` and only that route set can call it. Task 4 exports it so the scan route can ask who is signed in |
| `scans` | No owner column and none is added: the link is a separate table, so "a scan holds no visitor data" stays true |
| The worker's role | `arablyzer_worker` reads, updates and deletes `scans` and reads nothing of the accounts. The retention sweep must not delete scans an account keeps, so it gets one column: `SELECT (scan_id) ON account_scans`, not the table. A foreign-key cascade runs as the table's owner, so it needs no right of its own |
| Erasure | Better Auth deletes the `users` row; `sites` and `account_scans` go by cascade, but the scans and their reports would stay. A `beforeDelete` hook deletes the person's linked scans first, and a failure there stops the erasure (fail closed) |
| Plan numbers | The design leaves every free-plan number to the owner (§2.4). Development values are named `DEVELOPMENT_ACCOUNT_PLAN`; production with accounts on refuses to start without its own (the same rule as the abuse limits) |
| Home page | No account script may load there (§1.3). A signed-in person's scan form still sends Turnstile's token; the API simply ignores it when the cookie is good |

## Global Constraints

- Everything here is invisible and answers 404 with `ARABLYZER_ACCOUNTS` off. The anonymous scan path, tool scans, events and reports behave exactly as before.
- A cookie that is bad, expired, revoked, from another deployment, or whose store is down never blocks a scan: the request is an anonymous one.
- Plans and quotas are numbers from `packages/plans`, read at start; no number is written into a route or a string. Copy takes numbers as parameters from the API's answers.
- An account's limit is never below the anonymous one (checked at start) and never above the host and queue caps, which still apply to it.
- Nothing about a person but what M4.1 allows is stored; `sites` holds a URL the person chose, and goes with the account.
- UI on the R7 scale (`card p-card rounded-card`, `heading-2/3`, `text-body/small/meta`, `btn-grad`/`btn-white`, 44 px targets, logical `text-start/end`, no `style=` (CSP), no letter-spacing on Arabic). Every new Arabic string is `reviewed: false`.
- Commits `type(scope): subject`, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Lint, typecheck and the touched packages' unit tests before each commit.

## Review Focus

1. **Two adds at once at the limit.** The count and the insert are one transaction under a per-user lock: exactly the limit is stored, the rest are `403 plan-limit`. Task 2.
2. **The cookie is garbage / expired / the store is down** on `POST /api/scans`: the scan is refused or accepted exactly as for an anonymous visitor, never `401` or `500`. Task 5.
3. **Someone else's site.** `DELETE /api/sites/:id` and `POST /api/sites/:id/scans` for another person's id answer `404`, not `403`. Task 6.
4. **A signed-in user is not given less than a visitor**, and is not unlimited: the bucket refills at the plan's rate; a scan past it is `429` with `Retry-After`. Task 5.
5. **Erasure takes the scans with it** and the M4.1 test that searches every table for the person still finds nothing. Task 3.
6. **Retention** keeps a linked scan for the plan's days and an unlinked one for `ARABLYZER_REPORT_RETENTION_DAYS`, and the global sweep never deletes a linked one. Task 7.

## 2. Contracts

All JSON, `no-store`, Origin-checked like the rest; all 404 with accounts off.

| Route | Guards | Success | Refusals |
|---|---|---|---|
| `GET /api/sites` | session | 200 `{sites: SiteSummary[], limit: number}` | 401, 503 |
| `POST /api/sites {url}` | Origin, JSON, session | 201 `SiteSummary` (200 if already saved) | 400 (a URL code), 401, 403 `{error:'plan-limit', limit:'savedSites', plan}` |
| `DELETE /api/sites/:id` | Origin, session | 204 (its scans stay in the history) | 401, 404 |
| `POST /api/sites/:id/scans` | Origin, session | 202 `CreateScanResponse` | the scan route's, 401, 404 |
| `GET /api/account/scans` | session | 200 `{scans: AccountScan[], historyDays}` (newest first, at most 50) | 401, 503 |
| `POST /api/scans` | as before; with a good cookie, Turnstile is skipped and the account's bucket and place are used | 202 | as before |

`SiteSummary = {id, url, createdAt, lastScan: AccountScan | null}`; `AccountScan = {id, url, state, score: number | null, createdAt, siteId: string | null}`; a report's page is `/r/<id>` (or `/en/r/<id>`) from `id`.

**Settings** (read when accounts are on; production must set all five): `ARABLYZER_PLAN_ACCOUNT_SCANS` + `_SCAN_SECONDS` (the bucket), `ARABLYZER_PLAN_ACCOUNT_INFLIGHT`, `ARABLYZER_PLAN_ACCOUNT_SAVED_SITES`, `ARABLYZER_PLAN_ACCOUNT_HISTORY_DAYS`. Paid plans (`PRO`, `AGENCY`) read the same five names with their prefix, all or none, and nothing uses them until M4.4. The worker reads only the history days.

## Tasks

### Task 1: Plan numbers
`account-plan.ts` with `AccountPlan {id, scans: Window, inFlight, savedSites, historyDays}`, the development values, `planCatalogFrom(env, anonymous)` (account required; `pro` and `agency` all-or-none, else `null`; refuses a plan below the anonymous rate or in-flight), `accountHistoryDaysFrom(env)` (null with accounts off). Tests: development values, production refusal per variable, below-anonymous refusal, half a paid plan.

### Task 2: The tables and the account store
`sites (id, user_id→users cascade, url, created_at; unique (user_id, url))`, `account_scans (scan_id→scans cascade, user_id→users cascade, site_id→sites set null, source manual|monitor, created_at)`, indexes on `(user_id, created_at desc)`. `AccountData`: `sites`, `site`, `addSite` (transaction + `pg_advisory_xact_lock(hashtext(user))`, count, insert, `existing` on conflict), `removeSite`, `link` (finds the site by URL), `history`, `latestPerSite`, `eraseUser`. Memory version for unit tests and `dev.ts`. Tests: shared contract suite over both; on PostgreSQL, 12 adds at once at limit 5 store 5.

### Task 3: Erasure
`beforeDelete` in `createAuth` runs `eraseUser`; a throw stops the deletion. Extend the PostgreSQL erasure test: a user with a site and two scans leaves nothing in any table, and the scans' reports are gone.

### Task 4: Who is signed in
Export `identify` / `requireUser` from `mountAccounts`; `createApp` takes them for the scan route.

### Task 5: Quota, in-flight and Turnstile in `POST /api/scans`
After the attempt counter: `identify`. A user skips Turnstile, takes `account:<id>` from the plan's bucket (not `connection:`), holds a place under `account:<id>` with the plan's `inFlight`, then the shared network, host and queue steps; a whole-page scan is linked (`manual`) after it is stored, and a link that fails fails the scan. Tests per Review Focus 2 and 4, plus: anonymous path unchanged (no `identify` call without a cookie).

### Task 6: The sites routes
`apps/api/src/sites.ts` over the contract. The saved URL is the checked one (`parseTarget`), so the scan finds it again by equality. Tests: add/list/duplicate/limit, other person's id is 404, scan-from-site is quota-counted, accounts off is 404.

### Task 7: Retention by plan
`deleteOlderThan(before, 'unlinked' | 'linked')` (default `unlinked`); the worker sweeps linked scans older than the account plan's days when accounts are on. Provision grants the worker the one column. Tests: memory and PostgreSQL, linked kept by the global sweep, deleted by the plan sweep; the worker's role cannot read `account_scans.user_id`.

### Task 8: The page
`SitesPanel` on `/account` (only when signed in): saved sites with last score, add form, scan now (then the report), remove; recent scans with score and link; "n of N sites" and the history days from the API. Pure helpers in `sites-model.ts` with unit tests; the browser test's route mock extended.

### Task 9: Settings, CI, the record
Compose, `.env.example`, README "Accounts", the stack's settings in CI, the Record below.

## Acceptance criteria

1. With the flag on: a signed-in person adds, lists, scans and removes sites, sees their history with scores, hits `plan-limit` at the saved-sites number, `429` at the scan bucket, and erases everything; with it off every route is 404.
2. Anonymous scans, tool scans, events, reports and deletion behave as before; a bad cookie is an anonymous request.
3. The retention sweep keeps linked scans for the plan's days; the worker's role still reads no account data.
4. The M4.1 erasure test finds nothing; `pnpm lint`, `format:check`, `typecheck`, `test:unit`, `test:services`, `test:browser`, `site:audit`, `test:stack` pass.

## Not in M4.2

Monitors and the scheduler (M4.3); subscriptions and plan changes (M4.4), so every account is on `account` and `planOf` is the one place that changes; the pricing page; crawl; export.
