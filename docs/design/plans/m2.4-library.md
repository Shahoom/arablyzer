## 1. The rule library (M2.4a)

**A page per rule, in both languages**, in the approved Rule board: the heading; chips with the rule's id, severity,
category, version and what it reads (the HTML, robots.txt, browsers, Chrome's data); why it matters; the live example;
how to fix; how we detect, as numbered steps; the references. Beside it: its weight in the score (from
`packages/scoring`, so the page cannot drift from the score), the tools that run it and the full scan, and rules of its
category. JSON-LD: a `TechArticle` with the rule's version, and the breadcrumb.

**The live example** (§6.2 «مثال حي») is an excerpt of the rule's own fixtures, `rules/<id>/example.md`: two code
blocks, the wrong and the right. A test holds each to the truth: the wrong one is in a `wrong*` fixture and in no
`right*` one, the right one the other way round, whitespace aside. The fixtures are what the rule's tests run (and, for
the rules that render, what the engine's browser suite renders in three engines), so the page shows exactly what the
rule judges. The same excerpt serves both languages, as the fixtures do. Seven rules show none, since what they judge is
not in the page's files: the three Core Web Vitals (Chrome's visitor data), the certificate, HTTPS, the HSTS header and
compression; their fix sections show the code to write.

**The library's index** lists the rules by category, the Arabic layer first, with the same search as the tools'
directory. "Rule library" joins the header.

**Links in.** Every rule a tool page runs links to its page, and so does every finding in a report and a tool's result
(BUILD-PLAN §6.2: «كل مخالفة في أي تقرير تربط هنا»).

**The self-audit** holds every rule page to the template: the sections in order (the example when there is one), text
in each, a link to a source in the references, the `TechArticle` and the breadcrumb, and everything every page needs.
Lighthouse and the three-engine self-scan take the first rule page in each language, as for the tool pages.

**A page about a problem shows the problem.** The tatweel rule's page quotes a stretched word, the digits rule's page
Eastern and Persian digits, the prices rule's page a price with two decimals, and the site's own rules failed those
pages. The rules already leave text in code alone (`code`, `pre`, `kbd`, `samp`), which is where a quoted sample
belongs: the copy writes them in backticks, as the tools' copy does. Nothing is exempted.

## 2. The bot (M2.4b)

**What the plan asks** (§13): a scan a person asks for is a browser's visit with a named user agent; the deep crawl and
the yearly crawl respect robots.txt; `/bot` explains the bot and lets a site opt out.

**The opt-out.** A site that names ArablyzerBot in its robots.txt and disallows a page is not scanned there: the scan
reads robots.txt before the page, stops, and the report says the site asked not to be checked. Only a group that names
the bot counts: `User-agent: *` addresses crawlers, and a scan someone asks for is not a crawl. Every scan reads
robots.txt afresh, so the opt-out holds from the next scan. A list of sites excluded on request needs a contact address,
which is the owner's (§20).

**`/bot`** says who the bot is and what it does, from the code: its user agent, when it visits (only when someone asks
for a check of that page), what it fetches, what it never does (submit a form, type into a field, log in, get past a
challenge), its limits, and how to opt out.

**`/methodology`** renders `docs/methodology.md`, the Arabic at `/methodology` and the English part at
`/en/methodology`: the page the tool pages and the reports link to, on the site instead of GitHub.

**404 pages** in both languages, the English one for paths under `/en/`, served by Caddy with the 404 status.

## 3. Being found (M2.4c)

- **robots.txt** allows everything but `/api/`, and names the sitemap. Reports stay crawlable, so search engines can
  read their `noindex`.
- **Sitemaps**: an index at `/sitemap.xml` and one sitemap per section (`pages`, `tools`, `rules`; `fix` and `glossary`
  when they come), each URL with its hreflang alternates, and `lastmod` where a page has a date (the tools' `updated`).
  Written at build for the site's origin.
- **IndexNow**: the key is the deployment's (`ARABLYZER_INDEXNOW_KEY`); the build writes its key file, and
  `pnpm indexnow` sends the changed URLs after a deploy. Deploying is the owner's decision, so nothing is sent before.
- **Open Graph images**: one 1200×630 image per page, drawn by Chromium at build from a template in the Lab design, so
  Arabic joins as it does on the page. The `og:image` gap the audit has carried since M2.1 closes.

## 4. `/fix` and the glossary (M2.4d)

- **`/fix`**: a guide per Search Console or Merchant Center message, titled with the message as Search Console shows it,
  in Arabic and in English (people paste the message into a search), then what it means, why it happens, how to fix it,
  and the Arablyzer tool or rule that checks it. The first fifteen are the Page indexing report's reasons, taken from
  Google's documentation, not from memory.
- **`/glossary`**: a page per term, with the English term, a short definition, an example and links to the tools and
  rules that use it. No page without enough to say: a thin page is worse than none (§6.5, doorway pages).
