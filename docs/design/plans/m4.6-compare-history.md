# M4.6 Report Comparison and Score History — Implementation Plan

> **ملخص للمالك:** المعلم السادس من المرحلة 4: من سجّل الدخول يضغط «قارن مع السابق» بجانب أي فحص في سجله، فيرى صفحة تقول ما **أُصلح** وما **ظهر جديداً** وما **ساء** وما بقي كما هو، وفرق الدرجة العامة ودرجة كل فئة، وما اختلف بين المتصفحات الثلاثة. وكذلك يقارن زحفين عميقين لموقع واحد على مستوى القالب («مشكلة العنوان في قالب المنتج: كانت 38 من 40 صفحة وصارت 4»). وفي كل موقع محفوظ مخطط لدرجاته (العامة وكل فئة) على مدى أيام سجل الخطة، يجمع الفحوص اليدوية وفحوص المراقبة، وعليه علامات حيث نبّهت المراقبة. لا شيء جديد يُخزَّن (لا جداول)، ومطفأ مع `ARABLYZER_ACCOUNTS`. **المطلوب منك:** نصوص الواجهة العربية (`reviewed: false`).

**Goal:** A signed-in person compares two reports of one site (page scans, and crawls by template) and sees a saved site's scores over time, with the monitoring alerts marked.

Design source: `docs/design/phase-4.md`. Built on `m4.2-sites.md` (account scans, history days), `m4.3-monitoring.md` (monitor runs, the alert decision in `monitor/evaluate.ts`) and `m4.5-deep-crawl.md` (crawl reports, templates).

## 0. Measured before planning (2026-10-09)

| Question | Result |
|---|---|
| Is there a diff to reuse? | `Finding.fingerprint` ("stable hash of rule + location; used to diff scans") is what the monitor's "new critical" uses. It is not enough for a comparison: a location that moved a little (a line number, a numbered selector) changes it. The comparison matches on rule + normalised selector and address, and falls back to the snippet. |
| What a report holds per category | `report.score.categories` (null when no rule weighed), `score.overall`, `score.rules {ran,total}`, `generator.rulesetVersion`; `scan.render[]` per engine with a status; a finding's `evidence.engines` for the rendered ones. Enough for every number asked for; no new scan data. |
| Are alerts stored? | No. A run keeps only `notified`. The decision (`factsOf`, `eventsOf`) is pure on two scans and the person's thresholds, so the markers are **derived** from the points with the person's current thresholds, not stored. The chart says so in one line. |
| What the history needs per scan | overall, category scores, critical fingerprints (for the "new critical" alert), state, source. The list query (`history`) has the overall only. One new store query reads the three from the report column (`jsonb_path_query_array` on PostgreSQL), so no report is shipped to the API. |
| Ownership | `account_scans` links a scan to a person. A comparison is of two of the caller's own scans; another person's id is a `404`. |
| Crawl reports | Computed on read from rows (`buildReport`). The comparison builds both and matches on rule + rendered? + **template pattern** (a template's key `t3` is per crawl; its address shape is what lasts). |

## Global Constraints

- Invisible and 404 with `ARABLYZER_ACCOUNTS` off; no new table, no new personal data, so erasure and retention are unchanged (a comparison is computed on read from scans the account already keeps; history is limited to the plan's `historyDays`, which the sweep enforces anyway).
- Read-only, session-guarded, `no-store`; no body, so no Origin guard beyond the session's (as the other `GET`s). Ids are checked against their patterns before any lookup.
- A scan that is not complete, has no report, is a tool's scan, or belongs to another site is `422 {error:'not-comparable'}`; another person's, or an unknown, is `404`.
- Everything the API sends is capped: at most 400 finding changes (the unchanged ones last), 200 history points, 60 markers.
- Chart: server data, client SVG (a Preact island), no library; `role="img"` with a title and a text summary, a real table as the fallback, colours from the existing tokens, drawn right-to-left in Arabic (the oldest point at the inline start), no animation (so nothing to stop under reduced motion), 44 px targets for its controls.
- UI on the R7 scale (`card p-card rounded-card`, `heading-2/3`, `text-body/small/meta`, `chip`, `btn-grad`/`btn-white`, logical `text-start/end`, no `style=` (CSP), no letter-spacing on Arabic). Every new Arabic string is `reviewed: false`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Matching is deterministic and fair to repeats**: ten findings of one rule at ten selectors match one to one; two with the same key match by occurrence, not all to one. Task 2.
2. **Not someone else's, not another site's**: `404` for a scan that is not linked to the caller, `422` for two sites. Task 4.
3. **Markers equal what the monitor would have sent** for the same two scans and thresholds (they call the same `eventsOf`). Task 3.
4. **The chart is usable without sight and without colour**: summary text, a table with every value, the series told apart by a label and a dash as well as a colour. Task 6.
5. **RTL**: the time axis runs right to left in Arabic and the value labels sit at the inline start. Task 5.

## 2. Contracts

| Route | Success | Refusals |
|---|---|---|
| `GET /api/compare/scans?base=<scanId>&head=<scanId>` | `ScanComparison` | 400, 401, 404, 422 `not-comparable` |
| `GET /api/compare/crawls?base=<crawlId>&head=<crawlId>` | `CrawlComparison` | 400, 401, 404, 422 `not-comparable` |
| `GET /api/sites/:id/history` | `SiteHistory` (the plan's days, oldest first) | 401, 404 |

`base` is the earlier report, `head` the later: the sentences read "from base to head". The page link is `/account/compare?type=scan|crawl&base=…&head=…` (`/en/account/compare`).

**Finding matching.** Key = rule id + selector + address (selector whitespace collapsed; address without scheme, fragment, trailing slash, `utm_*`/`fbclid`/`gclid`; query sorted) or, with neither, the snippet (whitespace collapsed, lower case, 120 characters). The n-th finding with a key in `base` matches the n-th in `head`. Matched: more severe in `head` → `worsened`, less → `improved`, same → `unchanged`. Only in `head` → `new`, only in `base` → `fixed`.

**Crawl matching.** Key = rule id + rendered? + template pattern. Share = pages ÷ checked. `new`/`fixed` when absent on one side; `worsened`/`improved` when the share moved 10 points or more or the severity changed; else `unchanged`. Score = the mean of the representatives' browser scores, overall and per template pattern.

**Markers** (monitor runs only): `score-drop` (the drop is the person's threshold or more), `critical` (new critical fingerprints, when the person wants them), `down` (the first unreachable run of a stretch). Same functions as the scheduler, the person's current settings.

## Tasks

1. **Contract and store** — shapes and paths; `linkedScans(userId, ids)` and `scorePoints(userId, siteId, since, limit)` on memory and PostgreSQL; contract tests on memory, PostgreSQL service test.
2. **The pure comparison** — `normalize`, `compareScans`, `compareCrawls`; unit tests (repeats, severity change, categories only on one side, engines, ruleset mismatch note, template pattern match).
3. **History and markers** — `siteHistory(points, wants)`; tests for each marker and for "same as the scheduler".
4. **Routes** — `compare.ts`; tests: happy paths, 404 for another person's, 422 for two sites / a tool scan / an unfinished scan, accounts off is 404, anonymous 401.
5. **Chart model** — scales, ticks, paths, RTL mirroring, series; unit tests.
6. **UI** — the compare page, the chart island in each site's card with the table fallback, «compare with previous» in the scan history and on the crawl report; AR + EN copy; guards and API client with tests; the browser test's mock extended.
7. **Checks, CI, the record.**

## Acceptance criteria

1. Flag on: two scans of one saved site compare to fixed / new / worsened / improved / unchanged findings, per-category and overall deltas and per-engine differences; two crawls compare by template; the site card draws its history with alert markers; every refusal above holds.
2. Flag off: all three routes 404, the page is not linked; anonymous scans, tools and reports unchanged.
3. `pnpm lint`, `format:check`, `typecheck`, unit tests, web build, `site:audit` pass.

## Not in M4.6

Comparing a scan with an anonymous (unlinked) report, exporting a comparison, three-way comparison, stored alert history (the markers are derived), per-template score history, charts for a crawl, per-category lines beyond the ones the person switches on.
