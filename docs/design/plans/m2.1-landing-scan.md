## 1. M2.1a — `apps/web`

- **Astro, static.** `build.format: 'preserve'`, so pages land where `PATHS` in `packages/seo` says (`/`, `/en/`,
  and `/tools/<slug>` in M2.2). React only in islands; everything else is Astro components with no JavaScript.
- **The site's origin** comes from `ARABLYZER_SITE` at build time and is `PREVIEW_SITE` (`https://arablyzer.example`)
  until the domain decision (BUILD-PLAN §20.1). Canonical and hreflang come from `alternates()`, and `<head>` from
  `renderHead()`: one source for both the old templates and the site.
- **Design tokens** (the approved Lab system) as Tailwind 4 `@theme` variables in `src/styles/global.css`: paper,
  ink, rules, signal, severities, measure blue, the instrument panel, the ten category colours, the two grids.
  Sharp corners; the offset shadow only on the key element. Logical properties only (`ms`/`me`, `ps`/`pe`,
  `start`/`end`, `border-s`/`border-e`); the self-scan runs our own `rtl-physical-css` on the built CSS.
- **Fonts:** IBM Plex Sans Arabic 400, 500, 600, 700 (Arabic and Latin subsets) and IBM Plex Mono 400, 500, 600
  (Latin), `font-display: swap`, metric-matched fallbacks; which files to preload is measured with Lighthouse.
- **Links only to pages that exist.** The header and footer list the pages the site has; the rest appear with
  M2.2–M2.4. A link to a missing page fails the self-audit.
- **Content from the engine:** `src/lib/showcase.ts` reads the golden reports at build time and picks the findings
  by rule id: the hero's instrument panel, the four Arabic-layer examples with Arablyzer's own words, and the terminal
  panel, which is the CLI's own `formatReport()` output for report 04 (its timing lines left out, since golden reports
  zero the durations). A missing finding fails the build's tests.
- **Copy** in `packages/i18n`, typed alike in both languages, with a `reviewed` flag the `arabic-copy` CI job reads,
  as for rules. English is written for English readers, not translated word for word.

## 2. M2.1a — the scan form

- One React island, `ScanForm`, in the hero (`client:load`) and in the closing call to action (`client:visible`).
- It checks what the browser can (http or https, at most 2,048 characters) and sends `POST /api/scans`; the API
  checks everything again. On success it opens `/r/{id}`.
- `packages/api-contract` holds the request, the response and the error codes, as Zod schemas for the API and plain
  types for the island, so the island ships no Zod.
- Every error the API can give has its own words: an address Arablyzer does not scan, the limit reached (with when
  to try again), the check that the visitor is human failed, the service unavailable. Until M2.1b, the page runs
  against no API and says the service is unavailable.
- Without JavaScript the form cannot pass Turnstile, so a `<noscript>` note says the scan needs JavaScript.

## 3. M2.1a — checks in CI

- **Site self-audit** (`checks` job): the site is built, and every page in `dist` is audited as the tool pages are
  today: `lang` and `dir`, one `<title>`, a description, one `<h1>`, canonical, reciprocal hreflang, JSON-LD that
  parses, indexable, internal links that resolve to built pages, and our own HTML rules.
- **Self-scan** (`browsers` job): `dist` served on loopback and scanned by `scan()` with the three engines; no rule
  may fail or error except the three that judge the server (`https-missing`, `hsts-missing`, `tls-expiring`),
  which the staging site answers in M2.5. The runner is a throwaway VM and the pages are ours, so WebKit runs there
  with `networkIsolated`, as the browser SSRF suite does.
- **Lighthouse** (`browsers` job): all four categories on every built page, phone and desktop, three runs each,
  the site served with gzip as a production server sends it. The gate reads the median run: accessibility, best
  practices and SEO 100; performance at least 95 on the phone and 100 on the desktop, from CI's own numbers (§7).

## 4. M2.1b — the API and the worker (outline; detailed before the PR)

- `packages/plans`: the anonymous scan limit. The number is the owner's decision (Phase 2 design §7.2); until then a
  development value, named as such.
- `apps/api` (Hono, Zod): `POST /api/scans` checks the URL as the CLI does (http or https, 2,048 characters, DNS
  resolved, private and the server's own addresses refused), then Turnstile (Cloudflare's test keys in development),
  then the per-connection and per-target limits in Valkey, then queues the scan and answers `202 {id}`.
  `GET /api/scans/:id/events` streams progress (SSE); `GET /api/reports/:id` returns the report with
  `X-Robots-Tag: noindex`. IDs are random and unguessable.
- `apps/worker`: takes scans from BullMQ, one browser per worker (BUILD-PLAN §11), runs `scan()` with the three
  engines behind the egress proxy, stores the report, and publishes progress. The engine gains an `onProgress` hook.
- Storage behind interfaces: in memory for tests and local development; PostgreSQL (Drizzle) and BullMQ on Valkey
  in Compose and staging, tested in CI with service containers.
- The Turnstile call is the API's only outbound request that is not scan traffic; the lint allows `fetch` in that
  one file.
- SSRF tests on the API: every address class the egress tests refuse is refused before it is queued.

## 5. M2.1c — the report page and Compose (outline; detailed before the PR)

- `/r/[id]` is one static page, `noindex`, that the server sends for every report ID with `X-Robots-Tag: noindex`.
  An island follows the scan (the approved Audit-Progress design), then shows the report (the Report design; the
  schematic diagrams are drawn from `evidence.box`), or one of the four honest states (the States design).
- `infra/compose.yaml`: Caddy (the site, and `/api` to the API), the API, the worker, Valkey, PostgreSQL, and
  Smokescreen; the worker on a network whose only way out is Smokescreen.
- End-to-end: the golden sites scanned through the whole path, from the form to the report page.

**What our own checks found on our own page, and what changed:**

| Check | Finding | Change |
|---|---|---|
| Self-audit, `price-decimals` | The page shows «12.50 ر.ع.» as the wrong example, so our rule failed it | Quoted findings and sample prices are marked as the program's output (`<samp>`), which rules read as samples, as they read code |
| Self-scan, `a11y-color-contrast` | The Arabic-rendering chip's violet was 4.48:1 on its tint | `#6d4aff` became `#6844f5` (4.89:1) |
| Self-scan, `ar-font-no-arabic` | «العربية» on the English page was set in IBM Plex Mono, which has no Arabic letters | Set in the Arabic face |
| Self-scan, `og-tags-missing` | No `og:image` | A known gap until the site's Open Graph images (M2.4), listed with the self-audit's (`KNOWN_GAPS`) |
| Self-scan, needs review | Text over the grid, a CSS gradient, whose contrast axe cannot compute | Computed instead. Along a 120 px line, which lies on a 24 px one, the paper `#f3f5f7` darkens to `#dee0e3`: the lightest grey text, `#56606c`, is 4.83:1 there, and the signal colour `#b53a17` was 4.43:1, so it became `#b03815` (4.64:1), a shade darker. At the one-pixel points where two 120 px lines cross, the paper is `#cbced0`: 4.03:1 and 3.87:1. Those points are a pixel each, every 120 px; the text around them is above 4.5:1 |
| Lighthouse, accessibility 93 | The «نقيس، ولا نخمّن» list nested its `dt` and `dd` too deep | `dl > div > dt, dd`, the icon inside the `dt` |

**Lighthouse in CI** (run 36462827965, three runs each, the same in all three): `/` phone 96, `/en/` phone 97, every
desktop run 100, and accessibility, best practices and SEO 100 everywhere. The gate is set from these: 95 and 100.

**Lighthouse, measured on the owner's Mac (2026-09-28, three runs, median):**

| | Performance | Accessibility | Best practices | SEO |
|---|---|---|---|---|
| `/` phone | 95 | 100 | 100 | 100 |
| `/` desktop | 100 | 100 | 100 | 100 |
| `/en/` phone | 97 | 100 | 100 | 100 |
| `/en/` desktop | 100 | 100 | 100 | 100 |

The phone's performance began at 88 and 91. What moved it: the CSS inlined (no stylesheet request before the first
paint), the scan form's JavaScript loaded when the page is idle (React no longer competes with the first paint), and
the sections below the first screen laid out as they come near (`content-visibility`), which halved the style and
layout work. Two font files stay preloaded per page: without them, the Arabic text reflowed when its font arrived
(layout shift 0.225). What would move it further, measured: Fontsource's Arabic file is 43 KB a weight; the Arabic
block alone (U+0600–06FF, every letter of every language written in it, so no word splits across files) is 29 KB.
That subset is a build step (harfbuzz), proposed for M2.2 if CI's numbers call for it.

**Promises the page makes that the next pieces must keep** (the independent review, 2026-09-28): the code is open
and on GitHub (the repository is private: the owner opens it before the site is public); a visitor's address is
used for the limits alone and deleted within days (M2.1b: the limiter keys it by an HMAC, and its keys expire with
the bucket, tested); a report opens by its link alone and never appears in search engines (M2.1b: `X-Robots-Tag` on
the API, tested; M2.1c: the report page's own `noindex`).
