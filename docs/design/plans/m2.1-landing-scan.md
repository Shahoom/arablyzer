## 1. M2.1a — `apps/web`

- **Astro, static.** `build.format: 'preserve'`, so pages land where `PATHS` in `packages/seo` says (`/`, `/en/`,
  and `/tools/<slug>` in M2.2). React only in islands; everything else is Astro components with no JavaScript.
- **The site's origin** comes from `ARABLYZER_SITE` at build time and is `PREVIEW_SITE` (`https://arablyzer.example`)
  until the domain decision (BUILD-PLAN §20.1). Canonical and hreflang come from `alternates()`, and `<head>` from
  `renderHead()`: one source for both the old templates and the site.
- **Design tokens** (the approved Lab system) as Tailwind 4 `@theme` variables in `src/styles/global.css`: paper,
  ink, rules, signal, severities, measure blue, the instrument panel, the ten category colours, the two grids.
  Sharp corners; the offset shadow only on the key element. Logical properties only (`ms`/`me`, `ps`/`pe`,
  `start`/`end`, `border-s`/`border-e`); the self-scan runs our own `rtl-physical-css` on the built CSS.
- **Fonts:** IBM Plex Sans Arabic 400, 500, 600, 700 (Arabic and Latin subsets) and IBM Plex Mono 400, 500, 600
  (Latin), `font-display: swap`, metric-matched fallbacks; which files to preload is measured with Lighthouse.
- **Links only to pages that exist.** The header and footer list the pages the site has; the rest appear with
  M2.2–M2.4. A link to a missing page fails the self-audit.
- **Content from the engine:** `src/lib/showcase.ts` reads the golden reports at build time and picks the findings
  by rule id: the hero's instrument panel, the four Arabic-layer examples with Arablyzer's own words, and the terminal
  panel, which is the CLI's own `formatReport()` output for report 04 (its timing lines left out, since golden reports
  zero the durations). A missing finding fails the build's tests.
- **Copy** in `packages/i18n`, typed alike in both languages, with a `reviewed` flag the `arabic-copy` CI job reads,
  as for rules. English is written for English readers, not translated word for word.

## 2. M2.1a — the scan form

- One React island, `ScanForm`, in the hero (`client:load`) and in the closing call to action (`client:visible`).
- It checks what the browser can (http or https, at most 2,048 characters) and sends `POST /api/scans`; the API
  checks everything again. On success it opens `/r/{id}`.
- `packages/api-contract` holds the request, the response and the error codes, as Zod schemas for the API and plain
  types for the island, so the island ships no Zod.
- Every error the API can give has its own words: an address Arablyzer does not scan, the limit reached (with when
  to try again), the check that the visitor is human failed, the service unavailable. Until M2.1b, the page runs
  against no API and says the service is unavailable.
- Without JavaScript the form cannot pass Turnstile, so a `<noscript>` note says the scan needs JavaScript.

## 3. M2.1a — checks in CI

- **Site self-audit** (`checks` job): the site is built, and every page in `dist` is audited as the tool pages are
  today: `lang` and `dir`, one `<title>`, a description, one `<h1>`, canonical, reciprocal hreflang, JSON-LD that
  parses, indexable, internal links that resolve to built pages, and our own HTML rules.
- **Self-scan** (`browsers` job): `dist` served on loopback and scanned by `scan()` with the three engines; no rule
  may fail or error except the three that judge the server (`https-missing`, `hsts-missing`, `tls-expiring`),
  which the staging site answers in M2.5. The runner is a throwaway VM and the pages are ours, so WebKit runs there
  with `networkIsolated`, as the browser SSRF suite does.
- **Lighthouse** (`browsers` job): all four categories on every built page, phone and desktop, three runs each,
  the site served with gzip as a production server sends it. The gate reads the median run: accessibility, best
  practices and SEO 100; performance at least 95 on the phone and 100 on the desktop, from CI's own numbers (§7).

## 4. M2.1b — the API and the worker

**Packages.** `packages/plans` (the limits), `apps/api` (Hono on Node), `apps/worker` (BullMQ), and additions to
`packages/api-contract` (the progress events) and `packages/engine` (an `onProgress` hook).

**The path of one scan:**

1. `POST /api/scans` `{url, turnstileToken}`, at most 8 KB. The URL is checked as the CLI checks it: `checkUrl`,
   then DNS with `resolveEndpoint`, under a policy that refuses private, loopback, link-local, CGNAT and metadata
   ranges and the server's own addresses (its interfaces, plus `ARABLYZER_DENY_CIDRS` for a public address it does
   not see, such as behind NAT). Then Turnstile, then the limits, then the queue. The answer is `202 {id}`, or a
   refusal with its code and HTTP status (400, 403, 422, 429, 503).
2. The worker takes the job (`{id, url}`, nothing about the visitor), runs `scan()` with the three engines behind
   the egress proxy, one browser at a time, with the plan's budgets (§11), publishes each step, and stores the
   report.
3. `GET /api/scans/:id/events` streams the steps (SSE) from the start, so a page opened late, or reconnecting with
   `Last-Event-ID`, misses none: queued, started, the page fetched, robots.txt, each engine started and finished,
   CrUX, the rules, then done or failed.
4. `GET /api/reports/:id` returns the report, with `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store`.

**Turnstile goes through the egress package.** The plan says every request the server makes leaves through the
proxy (§13), so the API checks tokens with `safeFetch`, which takes a JSON POST since M1.3b; no lint exception is
needed. Development and tests run without it (`TURNSTILE_SECRET` unset, never in production), or with Cloudflare's
test keys.

**Limits** (`packages/plans`): scans per connection per window, scans of one host per window from everyone, and the
queue's length. The numbers are the owner's decision (Phase 2 design §7.2); until then `DEVELOPMENT_LIMITS`, named
as such, and production refuses to start without them set. The per-connection limit is a token bucket in Valkey,
keyed by an HMAC of the address under a daily key, so Valkey never holds an address, and its keys expire when the
bucket refills (§14). Behind Cloudflare the address is `CF-Connecting-IP`, trusted only when
`ARABLYZER_TRUST_PROXY` says so; otherwise the socket's.

**Storage behind three interfaces**, each with an in-memory version for tests and local development:
`ScanStore` (PostgreSQL through Drizzle: the scan's URL, status, times, score and report; no visitor data),
`ScanQueue` (BullMQ on Valkey), and `ScanEvents` (a Valkey stream per scan, trimmed and expiring with it). CI runs
the Valkey and PostgreSQL versions against service containers. `pnpm --filter @arablyzer/api dev` runs the API and a
worker in one process on the in-memory versions, so the site can scan locally with nothing else installed.

**Engine:** `ScanOptions.onProgress` receives each step as it happens. It never changes the report, and a listener
that throws cannot break a scan.

**Tests:** the routes on the in-memory stores; every address class the egress tests refuse, refused by the API
before anything is queued (`test:ssrf`); the limiter's refill; Turnstile's answers; the worker from job to report
on a golden page; the Valkey and PostgreSQL versions in CI.

**Left for later:** stopping a scan from its page and the screenshot the progress design shows (§5), and Caddy in
front (M2.1d, §5b).

## 5. M2.1c — the progress and report pages

- **One static page per language** (`/r/`, `/en/r/`), `noindex, nofollow`, with no canonical and no alternates. The
  site's server sends it for every `/r/{id}` (Caddy, M2.1d); in development, Astro's dev server does (the
  `arablyzer:report-route` integration). The header's and the footer's language links keep the ID.
- **An island** (`ReportApp`) reads the scan (`GET /api/scans/:id`). While it runs, it follows its events
  (`EventSource`, the only network API `events.ts` may use, by lint) and shows the approved Audit-Progress design:
  the engines the scan asked for (`started.engines`), the steps in the engine's order (the page, robots.txt,
  real-user data, the browsers, the rules, the score), one active at a time (a step the scan has no use for leaves
  the list once a later one began), and the log. Then it reads the report (`GET /api/reports/:id`) and shows the
  approved Report design: the score and its categories, the contents, the engines (one that shows a problem the
  others do not is marked), the notices, the problems with their evidence (selector, engines, snippet, and an
  overflow drawn to scale from `evidence.box`) and each rule's fix, and the passed and not-applicable rules. Or one
  of the honest states: the site refused the scan (HTTP 401, 403, 407, 429 or 503), a partial report, a scan that
  could not run, no report at that link, the service lost.
- **Each rule's fix** comes from the rules' Markdown, rendered to JSON before Astro runs (`scripts/generate.ts`),
  because Astro's build cannot read the rules' copy files. Short code in a fix never splits at a hyphen, and a
  table scrolls on its own on a phone.
- **"Scan again"** links to `/?url=…#scan`, and the form starts with that address; the scan starts only when the
  visitor sends it.
- **Left for later:** stopping a scan from its page, and the screenshot the Audit-Progress design shows (the engine
  keeps no screenshots yet).

**Tests:** the report model (events folded into progress, how a report opens, the problems' order), the form's
`askedUrl`, the report copy (counts and the engines' heading), the site self-audit of the report pages (`noindex`,
no canonical), and the manual checks recorded in §9.

## 5b. M2.1d — the stack (design)

**What designing it found (2026-09-28):**

- **A container on internal networks alone resolves no outside names.** Measured on Docker 29.5: on an
  `internal: true` network, `getent hosts` of a public name fails. A worker "on a network whose only way out is
  Smokescreen" cannot resolve; Smokescreen resolves, as the plan says it checks addresses "بعد حل DNS" (§13).
- **The worker as built runs the browsers and writes to PostgreSQL and Valkey.** The plan puts the browsers on a
  network that sees only the egress proxy, and no database (BUILD-PLAN §13, §18.3.1, "أهم شرط أمني"): a browser that
  a page compromised would otherwise reach the stores and their credentials.
- **Smokescreen has no rule for ports**, and the plan allows 80 and 443 alone. Read in its source (commit
  `6c44698`): it refuses its own addresses, those not global unicast, loopback, IPv6 that embeds IPv4, private
  ranges, CGNAT, and the ranges it is given; a proxy the client names in `X-Upstream-Https-Proxy` is vetted the same
  way before it is dialled.

**So:**

1. **`apps/scanner`** (new): the engine and its browsers behind a small HTTP interface for the worker alone.
   `POST /scan {url}` answers with the scan's progress events, then its report, as NDJSON, one scan at a time, and
   only with the token the worker holds. It holds no other credential, and sees two networks: the worker's and
   Smokescreen's.
2. **`apps/worker`** takes jobs, calls the scanner, and checks every event and the report against their schemas
   before it stores or publishes them. It runs no browser.
3. **The egress package's upstream mode** (`upstream` in the policy, from `ARABLYZER_EGRESS_PROXY`): `safeFetch`
   and the browsers' proxy keep every check that needs no DNS (scheme, port, credentials, internal names, literal
   addresses, redirects, the budgets) and send each connection through `CONNECT host:port` to Smokescreen, which
   resolves the name and refuses a refused address. Its refusals map to the same codes (`blocked-address`,
   `dns-failed`, `connect-failed`, `timeout`).
4. **Smokescreen**, built from source at a pinned commit, with a wrapper of a few lines that refuses any port but
   80 and 443 when it dials. Its deny list is generated from `packages/egress`'s ranges (CI checks they match), with
   the server's own public address (`ARABLYZER_DENY_CIDRS`).
5. **Networks:** `edge` (Caddy and the API: the API resolves names for its pre-check, and sends its own requests,
   Turnstile's, through Smokescreen); `data` (internal: the API, the worker, Valkey, PostgreSQL); `scan` (internal:
   the worker and the scanner); `isolated` (internal: the scanner and Smokescreen); `egress` (Smokescreen alone, to
   the internet).
6. **Caddy** serves the site, `/api` to the API, `/r/*` and `/en/r/*` from the report pages with
   `X-Robots-Tag: noindex`, compressed, with the security headers (CSP; HSTS behind TLS), and logs no addresses.
7. **Images:** one Dockerfile, a stage per service; the scanner's is Phase 1's scanner image (the browsers and fonts
   the golden reports hold for). The worker's `stop_grace_period` outlasts a scan's budget (120 s).
8. **End to end in CI:** the stack starts; the scanner reaches neither Valkey, PostgreSQL nor the internet except
   through Smokescreen; Smokescreen refuses every refused range and every port but 80 and 443; a golden site served
   inside the stack is scanned from the form to the report page (a test-only override opens that one address).

**Risks:** the scanner is one more hop and one more way to fail (the scanner away: the worker fails the scan and
its page says so); Smokescreen is Go, built in CI; CI's images are amd64, the owner's Mac builds arm64.

## 8. Record (M2.1b)

**Built:** `packages/plans` (the limits), `packages/store` (the scan store, queue, events and limiter, in memory
and on PostgreSQL, BullMQ and Valkey), `apps/api` (the routes, the URL check, the visitor's key, Turnstile through
the egress package, `server.ts` and `dev.ts`), `apps/worker` (a job to a stored report), the engine's `onProgress`,
the scan's events in the API contract, `serverPolicy()` in the egress package, and Turnstile on the form.

**Measured on the owner's Mac (2026-09-28):**

- The whole path in development (`dev.ts`, stores in memory, Chromium and Firefox): golden site 04 from
  `POST /api/scans` to its stored report, eleven events on the stream, score 90, the same three rules failed as in
  its golden report. The site's form, through Astro's dev proxy, started a scan and opened `/r/{id}`.
- The same path on PostgreSQL 16, Valkey 8 and BullMQ 6.3, as an integration test, and the stores' own tests on
  them: in CI's new `services` job, which fails without the services instead of skipping.
- The API's SSRF suite: 60 cases, every blocked range as an address and behind a name, loopback's other spellings,
  a name with one bad answer, internal names, credentials that hide the host, other ports and schemes, and the
  server's own address behind NAT; nothing stored or queued in any.

**Decisions made while building:**

- The stores moved to a package of their own: the worker writes to what the API reads.
- The queue's `add` answers nothing: the API counts the scans ahead before it adds, and publishes `queued` before
  the job exists, so a worker never starts a scan whose record or first event is missing.
- `bad-request` joined the refusal codes: a body that is not the form's is not a URL problem.
- BullMQ runs on ioredis 5.11, the version BullMQ itself is tested with.
- The `started` event names the engines the scan renders in, so the progress page counts to the engines it has.

**The independent review (2026-09-28)** found no way for a submitted URL to reach a refused address, and no visitor
data stored. What it found, verified by breaking things on purpose, and what changed:

| Found | Changed |
| --- | --- |
| A PostgreSQL restart ended the API and the worker (no `error` listener on the pool). | Both pools listen, with a connection timeout; Valkey's and the worker's errors are logged once every 30 s at most (`quietly`). |
| Each event stream held its own Valkey connection, with no limit. | Streams are capped per scan (8), per visitor (8) and per process (1,000); a scan that has ended is answered from its stored events with no connection, and 204 to a page that has them all. A shared reader per process is the next step if traffic needs it. |
| A worker that died mid-scan left it `running`, and BullMQ ran it again a minute later; a failed `started` publish could end the worker; a lost `done` turned a stored report into `failed`. | Scans move one way only (`queued → running → finished`, each move conditional), so a second run is failed, not scanned; the worker takes jobs with `maxStalledCount: 0` and fails the scan of any job that fails outside `runScan`; scans left running five scan budgets are failed every minute; events that cannot be sent are logged and the scan goes on; the report is kept before `done` is sent. |
| With Valkey paused or stopped, `POST /api/scans` never answered; a failed queue add left an orphan. | The API's Valkey connection queues nothing offline and times commands out at 5 s; any store failure answers 503 `unavailable`; a scan that could not be queued is failed and its page told. |
| Production's checks depended on `NODE_ENV` alone. | `server.ts` and `main.ts` apply them always; tests cover the API's refusals. |
| One IPv6 visitor had a bucket per address; a site had one per spelling of its name. | The visitor's key counts an IPv6 /64 and one spelling of an address; the host limit counts the registrable domain (Public Suffix List, through `tldts`), or the address itself. |
| Two service test files shared a Valkey database and flushed each other's (2 failures in 20 runs). | Each file has its own database: 0 failures in 20 runs. |
| The privacy answer said the IP was used for the limits alone, while Turnstile's check sent it to Cloudflare. | The API no longer sends it (`remoteip` is optional); the answer says no IP address is kept and names Cloudflare Turnstile. |

Also changed from its smaller findings: a `Last-Event-ID` past 2^64 − 1 reads from the start instead of failing;
a scan seen finished on a heartbeat gets its unread events, its real end among them, before any end is made up,
and a scan that could not run ends with `error`; shutdown ends open streams; the rate limiter's last update never
moves back, so a lagging clock adds no scans; Turnstile's answer must name the site's host (`ARABLYZER_SITE`, now
required in production); the form's wait for Turnstile ends on a timeout or an unsupported browser; the migration
holds an advisory lock; `apps/api` no longer exports a file it does not have.

Left for the owner's limits decision (Phase 2 design §7.2): Turnstile is checked before the visitor's limit, so a bad
token costs a request to Cloudflare, and the visitor's key changes at 00:00 UTC, which starts every bucket afresh;
with a daily window, that is a second allowance at midnight. For M2.1d's Compose file: the worker's
`stop_grace_period` must outlast a scan's budget (120 s).
