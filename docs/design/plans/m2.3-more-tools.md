# Arablyzer — M2.3: the rest of the forty tools

> The third milestone of Phase 2 (`docs/design/phase-2.md` §5): the tools of BUILD-PLAN §5.1 marked [MVP] that the
> rules of M2.2 cannot run. Each new rule comes as CLAUDE.md asks: its wrong fixture, its right fixture, its
> detector, a unit test, its copy in both languages for the owner to review, and its page in the rule library
> (M2.4). Written as the work goes, as the owner asked on 2026-09-29.

## 1. Three kinds of tool

M2.2's tools all take a page's address and run rules on it. The rest of §5.1 has two more kinds, which the template
of §6.1 allows («حقل رابط (أو لصق كود/ملف)»):

| Kind | What the visitor gives | Where it runs | Examples |
| --- | --- | --- | --- |
| `scan` | a page's address | the scanner, the tool's rules alone (M2.2) | security headers, redirect chains, sitemap |
| `paste` | text: robots.txt and a path | the visitor's browser, with the same code the rules use | robots tester |
| `generator` | a few fields | the visitor's browser: nothing leaves it | WhatsApp links, hreflang tags, JSON-LD, slugs |

A tool's definition says its kind. A generator or a paste tool still names the rules its output must satisfy, so its
page links to them and its examples are tested as a scan tool's are. The site's audit accepts, above the fold, a
form with an address field, a text area, or the generator's fields.

## 2. New rules

Each is deterministic and reads only what the scan collects; none sends anything the visitor did not ask for.

| Rule | Reads | Fails when |
| --- | --- | --- |
| `csp-missing` | the response's headers | no `Content-Security-Policy` header (a `<meta>` one counts) |
| `x-content-type-options-missing` | headers | no `X-Content-Type-Options: nosniff` |
| `frame-protection-missing` | headers | neither `frame-ancestors` in the CSP nor `X-Frame-Options` |
| `referrer-policy-missing` | headers | no `Referrer-Policy` (information: browsers have a safe default) |
| `redirect-chain` | the redirects followed | more than one redirect before the page |
| `redirect-temporary` | the redirects followed | a 302 or 307 where the move is permanent (http to https, host to host) |
| `sitemap-missing` | robots.txt and `/sitemap.xml` | no sitemap named in robots.txt, and none at `/sitemap.xml` |
| `sitemap-invalid` | the sitemap | not XML, or not a `urlset` or `sitemapindex` of the protocol |
| `js-only-content` | the HTML as sent and the rendered page | more than half of the Arabic words a browser drew (at least 20 of them) are not in the text of the HTML as sent, hidden text and `<noscript>` included |
| `spf-missing` | DNS TXT of the domain | no `v=spf1` record |
| `dmarc-missing` | DNS TXT of `_dmarc.<domain>` | no `v=DMARC1` record, or one without a valid `p` tag (`none`, `quarantine` or `reject`) |
| `link-broken` | the page's links to its own site: 1,000 counted at most, the first 50 asked for | a link answers 4xx or 5xx, other than 401, 403, 407, 429 and 503, which a site gives a visitor it takes for a bot |
| `payment-methods` | the page's HTML as sent: the names of its images, icons and controls, and the scripts it loads | information alone: the Gulf payment methods it shows (mada, Apple Pay, STC Pay, Tabby, Tamara) |
| `bot-challenge` | the page's answer | information: the site answers a named bot with a challenge (so AI crawlers may be refused too) |

The thresholds are the protocols' and the standards': "more than one redirect" is a chain; nothing counts as too
heavy or too slow without a number the owner or a standard sets. The parameters of a check's own method (how many links
it counts, asks for and asks at once, how long it waits, the fewest words a browser is judged on, "more than half") are
ours: the copy states each as ours, and one test takes every figure the copy states from the constant that does it
(`packages/engine/test/copy-figures.test.ts`). DNS lookups are for TXT records only: as DNS over
HTTPS (RFC 8484) through the egress proxy on the hosted service, whose scanner resolves no name itself, and with the
machine's own resolver where there is no proxy. `link-broken` follows the site's own links only. It counts 1,000 of them at most on a page, and asks for the first 50
that robots.txt does not keep from the bot (a group naming it, or the `*` group, since the links are not the visit
someone asked for), four at a time, within 20 seconds in all. Each link gets a `HEAD` request, then a `GET` where
`HEAD` answers an error or the connection fails, so a link can take two requests, each within 10 seconds; no redirect
is followed. A `401`, `403`, `407`, `429` or `503` is how a site turns away a visitor it takes for a bot, not an answer
about the link, and the checks stop at the first `429`. The report says how many links it did not check, and "at
least" past the 1,000.

## 4. Risks

- **Rules that read DNS and follow links** widen what a scan does: both go through the egress package, within the
  scan's budget, and the SSRF suite gains cases for them.
- **The generators' output must be right in every browser:** each has unit tests of its output against the rule it
  names.
- **Copy:** fifteen more tools and fourteen rules, in both languages, for the owner to review.

## 5. M2.3a: the security headers and the redirects (the design as built)

Three pull requests, as the rules come: **M2.3a** the response's headers and the redirects; **M2.3b** the paste tool
and the generators; **M2.3c** the sitemap, DNS, links, the rendered text, payments and challenges.

**The header rules** read the final response's headers, as `hsts-missing` does, and apply to a 2xx HTML page on a
public host: like `https-missing`, they leave local development hosts alone, where no deployment's headers are set.
Rules that read headers need a collector of their own, `headers`, which `hsts-missing` and four others moved to, so the
example test can tell them from the rules that read the connection (`https-missing`, `tls-expiring`).

| Rule | Severity | Fails when |
| --- | --- | --- |
| `csp-missing` | minor | no `Content-Security-Policy` header and no `<meta http-equiv="Content-Security-Policy">` in `<head>`; a `Content-Security-Policy-Report-Only` one enforces nothing and does not count |
| `x-content-type-options-missing` | minor | no `X-Content-Type-Options` header whose value is `nosniff` (case aside, the first value, as browsers read it) |
| `frame-protection-missing` | minor | neither a `frame-ancestors` directive in an enforced CSP header (a `<meta>` CSP cannot set it) nor an `X-Frame-Options` of `DENY` or `SAMEORIGIN` |
| `referrer-policy-missing` | info | no `Referrer-Policy` header or `<meta name="referrer">`: browsers default to `strict-origin-when-cross-origin`, so it is said, never deducted |

**The redirect rules** read the redirects the page fetch followed (the report's `target.http.redirects`, now in the
rules' evidence as `redirects`):

| Rule | Severity | Fails when |
| --- | --- | --- |
| `redirect-chain` | minor | more than one redirect before the page |
| `redirect-temporary` | minor | a 302 or 307 that only changes the scheme to https, or the host between `example.com` and `www.example.com`, or both at once: moves that are permanent by nature |

**The tools:** `security-headers` (the four and `hsts-missing`), `tls-check` (`https-missing`, `tls-expiring`,
`hsts-missing`), `redirect-chain-check` (the two redirect rules). Their examples are HTTP exchanges, which the example
test checks against the rules as it checks HTML. Their cards, and the pages of their rules, say they read the
server's response, not the HTML.

**The fixture server** serves a site under several names, with routes for one name, so a wrong fixture can move
`shop.example` to `www.shop.example`; a redirect to one of its own names keeps the server's port.


## 6. Record (M2.3a)

**Built:** the four header rules, the two redirect rules and their three tools of §5. The engine passes the redirects
a page's fetch followed to the rules, the fixture server serves a site under several names, and tools can show an
HTTP exchange as their example, which the example test checks against the rules.

**The independent review** found, and the branch fixed:
- `redirect-chain` failed the chain the HSTS preload list requires (HTTP to HTTPS on the same host, then to the
  canonical name), and its fix broke preload. A first redirect that only moves the address to HTTPS on the same name
  is no longer counted, and the fix keeps that step.
- `redirect-temporary` left out `303`, which Google lists with `302` and `307`; a scan only sends GET. Its copy said
  Google takes a temporary redirect as no signal. Google calls it a weak signal, and a permanent one a strong signal.
- `frame-protection-missing` passed `frame-ancestors *`, which lets any site frame the page and makes browsers ignore
  `X-Frame-Options`. It now fails with a message of its own.
- Labelling a rule by its `headers` need called four HTML rules, and four HTML tools with them, readers of the
  server's response. `SERVER_RESPONSE_RULES` in the rules package now names the rules that judge the server's
  response; the site's labels and its self-audit both read it.

**Left as they are:**
- `csp-missing` counts any enforced policy, one that limits no scripts included, as its copy now says.
- When the HTML cannot be read in time, `csp-missing` and `referrer-policy-missing` report an error even where a
  header already settles them.
- The site itself passes the new rules: every page carries its policy in a `<meta>` with the hashes of its scripts
  and styles (M2.1), and the server sends `X-Frame-Options`, `X-Content-Type-Options` and `Referrer-Policy`.

**Checked (2026-09-29, the owner's Mac):**
- Every package's tests (the rules' 1035 among them) but the golden reports', which CI regenerates for the new
  rules and golden pages.
- The site's self-audit (186 pages) and the SEO self-audit.
- Lint, types and formatting.

## 7. Record (M2.3b)

**Built:** four tools that run in the visitor's browser, with nothing typed leaving it. The WhatsApp link generator
writes the link WhatsApp documents from a number typed as people type it: with `+` or `00`, spaces, a trunk 0, or
Eastern Arabic digits, and a full number typed without its `+` while a country is chosen. The hreflang generator
writes one set of tags for every version of a page. The product generator writes a Product with one Offer, the price
with its currency's own decimals. The robots.txt tester judges a pasted file for an address and a crawler, naming the
rule and its line. Each runs the code of the rule it names (`whatsapp-link-format`, `hreflang-invalid-code`,
`product-offer-invalid`, and the robots matcher), from `@arablyzer/generators`; their pages' examples are judged by
those rules like every tool's. A tool's definition says its kind, and the site's audit takes a paste or generator form
(`data-tool-kind`) with a real field in place of the address field.

**Waiting:** `arabic-slug-generator`. The generator is written (`arabicSlug`), but its page cannot show a live
example, because no rule judges a slug. It waits for a rule on URL slugs, or for a kind of page that needs none.

**Checked (2026-09-29, the owner's Mac):** the site's self-audit (176 pages); a browser suite in which each tool, in
Chromium, Firefox and WebKit, gives the answer its code gives in Node, the currency's decimals included, which each
browser reads from its own data; the site scanning its new pages; unit tests, lint, types and formatting.

**Found on the way:** the site's own scan took the WhatsApp generator's link-text field for a phone field, since its
placeholder names WhatsApp, and a phone field shown right to left reverses a typed number. The field holds text in
either language, so it takes its direction from what is typed (`dir="auto"`), as do the generators' other free-text
fields.


## 8. Record (M2.3c, first half)

**Built:** the sitemap rules (`sitemap-missing`, `sitemap-invalid`), `bot-challenge`, and the tools `sitemap-check`,
`ai-access` and `core-web-vitals`. The engine reads the sitemaps robots.txt names, or `/sitemap.xml`, through the
egress package, and takes a page answered with a bot challenge for no page: a challenge is never got past (BUILD-PLAN
§13).

**The independent review** found, and the branch fixed, one commit for each of its eight items:
1. A hostile sitemap could hold the scanner's event loop for seconds to hours, or its memory past 1.6 GiB, where no
   timer fires: sax's namespace mode is quadratic in an element's attributes and declarations, and it checks its
   buffers once per write. The reader now runs sax without namespaces and resolves them itself, writes 64 KiB at a
   time, and answers "not XML" past 32 levels of nesting (`SITEMAP_MAX_DEPTH`), 256 attributes on an element
   (`SITEMAP_MAX_ATTRIBUTES`) and at what sax will not hold. The review's inputs each read in under 0.3 s, and 400,000
   URLs in 0.33 s, as before.
2. A page that answered with a challenge, a refusal or a 404 gave `complete` and a score of 100, because the rules
   beside the page (robots.txt, the sitemaps, the answer) passed. A scan that did not reach the page is now `partial`
   and has no score, overall or by category; `failed` stays for a page that could not be fetched or read. The CLI
   exits 2 for it, and the listing keeps NULL (a store test).
3. A browser could be answered a challenge the plain fetch was not, and run its script. The render now checks the
   headers of every answer to a request for the page itself with the same `challengeOf`, and that engine's run ends as
   `challenged`, with a notice naming the service. Lighthouse does not start after a browser met one.
4. A sitemap answering 401, 403, 407, 429 or a server error is one not checked, not a fault (RFC 9309 has a crawler
   read a 5xx robots.txt as unreachable, not missing); 404, 410 and an HTML page stay faults.
5. The first sitemap that could not be fetched ended the loop. Each sitemap now has an outcome of its own (fetched, an
   answer of the site's, or failed with the reason), the rules judge those read, and `Rule.couldNotCheck` lets a rule
   report an error only when what was read leaves it nothing. A relative `Sitemap:` line is still reported, and a
   `.xml.gz` that will not decompress fails `sitemap-invalid`.
6. Tests that passed with the code broken: the SSRF cases now name the code the policy gave, and a second fixture site
   listens where the policy does not let the scan (eight cases fail with every port open); three more bombs cost
   seconds to hours to read; and the example harness makes the sitemap state the engine makes.
7. Copy that said what the code did not, in both languages: a challenged page has no score; the report shows the
   `bot-challenge` notice (its card dropped every notice); `sitemap-missing` says robots.txt names no sitemap "as a
   full URL"; "3", "25 MB", "ten seconds" and the reader's limits are held to their constants by a test; the bot's
   page says what it does for a sitemap on another host.
8. Decided: CrUX is asked for a challenged page too (Google is asked, not the site); only the groups that name
   ArablyzerBot are honoured on a sitemap's host (the open question below); the ten seconds of the sitemaps are
   network time alone, after the render and Lighthouse, within what is left of the scan's 120 s.

The branch's own checks found two more: the sitemap checker's page reached 15 px past a phone's width in Arabic (a
tool's checks wrap their code now), and the report page of a blocked scan is tested in the browser with its challenge
notice.

**Left as they are:**
- **The render's guard is a tripwire, not a gate.** The page's answer is not held back until its headers are read.
  Measured with Playwright 1.63, holding it back changed too much: `route.fetch` gives the browser Node's answer
  (Firefox then met the proxy's 407 for every file, and the document's compression and encoding facts were lost), and
  a Chromium session that pauses responses takes the proxy's 407 of a plain HTTP request for the document's answer. A
  challenge's inline scripts may run for a moment and its script file may be asked for; a challenge is passed by what
  that file runs and asks, and the route lets none of it out.
- Lighthouse drives its own navigation, and puppeteer intercepts requests, not responses, so it cannot be stopped so.
  It is skipped once a render met a challenge; a scan that asks for Lighthouse without a render has no such warning.
- **Decided (2026-09-30):** a sitemap robots.txt names may sit on another host, whose robots.txt the scan reads
  first. A sitemap is a request of the scan's own, made as a crawler would, like a link: a group that names
  ArablyzerBot counts, and `User-agent: *` where none names it.
- A 404 or a 5xx is `partial` and has no score, as a refusal is; the report page shows only the refusals as blocked.
  `core-web-vitals` for a page behind a challenge says blocked, with the real visitors' findings under it.
- The Arabic of what items 5 and 7 changed or added is `reviewed: false`, like the rest.
- The hostile-sitemap tests fail by finishing late: the reader is synchronous, so a regression stalls them until CI's
  job limit, not their timeout.

**Checked (2026-09-30, the owner's Mac):**
- Every package's tests (2464 passed, the rules' 1097 among them) but the golden reports', which CI regenerates for
  golden pages 23 to 25: the engine's three golden-coverage tests fail until then, and no others.
- The SSRF suites (the egress package's 230, the API's 61) and the browser suites, in Chromium and Firefox (WebKit does
  not render on macOS): the browser package's 80, the engine's 41, Lighthouse's 9 and the site's 215.
- The CLI's end-to-end suite (163), and the store on a PostgreSQL (8; Valkey's tests skipped, there being no Valkey).
- The site's build and self-audit (198 pages, no problems).
- Lint, types and formatting, and the report schema's JSON unchanged.

## 9. Record (M2.3c, second half)

**The second independent review** found, and the branch fixed, one commit for each:
- **A CPU stall in the link checks.** `checkLinks` tested robots.txt for every link of the page, only to count the
  ones past the 50th: 100,000 links against 10,000 rules held the process for 65 s, and no timer, abort or health
  check could fire. robots.txt is now tested for the links taken alone, at most 1,000 links are counted (the total is
  then "at least"), the choice gives the event loop back every 20 ms, and `link-broken` reads no anchor when none is
  broken. Tests hold the wall clock and a timer's ticks.
- **The DNS rules could not run on the hosted service**: behind the egress proxy the engine asked no DNS, so both
  errored and every free audit was partial. TXT lookups now go as DNS over HTTPS (RFC 8484) through `safeFetch`, so
  through the proxy: `ARABLYZER_DOH_URL`, Cloudflare's resolver by default, written and read byte for byte in the
  egress package and tested against a local stand-in, the resolver's URL vetted like any request. A scan with no way to
  ask DNS leaves the rules out with the notice `dns-unavailable`. The form's note, the /bot page, the methodology and
  the copy say that the domain's name goes to that resolver.
- **Bot refusals read as broken links.** 401, 403, 407, 429 and 503 are no answer about a link (one constant, tied
  by a test to the report page's five); the checks stop at the first 429; a HEAD that fails to connect is asked again
  with GET.
- **Information rules counted as problems** ("3 problems to fix" for a store showing mada, Apple Pay and Tabby): a tool's
  headline, count, worst severity and fix link count the failures of rules that judge; a tool with only information
  findings says how many notes, and a tool of information rules alone says "nothing found" (`reportsOnly`, now in the
  rules package).
- **False positives in `js-only-content`**: the HTML as sent is all the body's text, hidden and `<noscript>` included;
  a browser is judged only when it drew at least 20 Arabic words; the message says what was measured. The scan asks for
  the HTML with no language preference and the browsers ask for Arabic; comparing with the document the browser
  received would mean reading its body in the browser package, so the copy states the limit.
- **The policy points the review settled**: link requests follow the `*` group of robots.txt; a site a platform gives
  its customers (`user.github.io`) has no domain to judge; a DMARC record needs a valid `p` tag; TXT records are
  sorted before the rules see them.
- **Tests that could not fail**: the link SSRF tests each fail without the layer they name; the budgets are tested with
  the constants the code uses; one test takes every figure the copy states from its constant.
- **Smaller**: a page's text alternatives are kept from both ends (1,000 each), and the payment copy says its lists of
  names are not exhaustive.

**Left as they are:**
- Text a script adds beside the page's own, such as a cookie notice, counts as words the HTML lacks, so a page with
  little text of its own can fail `js-only-content` for it; the copy says so.
- A site that picks its language on the server by `Accept-Language` can look script-written (see above).
- The golden reports for pages 31 to 34 come from CI, which also regenerates the others for the new rules.
- The site's own report page is script-written by design, like its missing `<h1>`: its browser tests accept
  `js-only-content` on it.

**Checked (2026-09-30, the owner's Mac):** lint, types and formatting; every package's tests but the golden reports'
three (`golden-coverage`), which wait for CI; the SSRF suites of the API, the egress package and the engine; the engine's
and the site's browser tests in Chromium, Firefox (and WebKit for the tool pages); the CLI's end-to-end tests; the
site's build and its self-audit (204 pages).
