# Arablyzer — M2.3: the rest of the forty tools

> The third milestone of Phase 2 (`docs/design/phase-2.md` §5): the tools of BUILD-PLAN §5.1 marked [MVP] that the
> rules of M2.2 cannot run. Each new rule comes as CLAUDE.md asks: its wrong fixture, its right fixture, its
> detector, a unit test, its copy in both languages for the owner to review, and its page in the rule library
> (M2.4). Written as the work goes, as the owner asked on 2026-09-29.

## 1. Three kinds of tool

M2.2's tools all take a page's address and run rules on it. The rest of §5.1 has two more kinds, which the template
of §6.1 allows («حقل رابط (أو لصق كود/ملف)»):

| Kind | What the visitor gives | Where it runs | Examples |
| --- | --- | --- | --- |
| `scan` | a page's address | the scanner, the tool's rules alone (M2.2) | security headers, redirect chains, sitemap |
| `paste` | text: robots.txt and a path | the visitor's browser, with the same code the rules use | robots tester |
| `generator` | a few fields | the visitor's browser: nothing leaves it | WhatsApp links, hreflang tags, JSON-LD, slugs |

A tool's definition says its kind. A generator or a paste tool still names the rules its output must satisfy, so its
page links to them and its examples are tested as a scan tool's are. The site's audit accepts, above the fold, a
form with an address field, a text area, or the generator's fields.

## 2. New rules

Each is deterministic and reads only what the scan collects; none sends anything the visitor did not ask for.

| Rule | Reads | Fails when |
| --- | --- | --- |
| `csp-missing` | the response's headers | no `Content-Security-Policy` header (a `<meta>` one counts) |
| `x-content-type-options-missing` | headers | no `X-Content-Type-Options: nosniff` |
| `frame-protection-missing` | headers | neither `frame-ancestors` in the CSP nor `X-Frame-Options` |
| `referrer-policy-missing` | headers | no `Referrer-Policy` (information: browsers have a safe default) |
| `redirect-chain` | the redirects followed | more than one redirect before the page |
| `redirect-temporary` | the redirects followed | a 302 or 307 where the move is permanent (http to https, host to host) |
| `sitemap-missing` | robots.txt and `/sitemap.xml` | no sitemap named in robots.txt, and none at `/sitemap.xml` |
| `sitemap-invalid` | the sitemap | not XML, or not a `urlset` or `sitemapindex` of the protocol |
| `js-only-content` | the HTML as sent and the rendered page | the rendered page's text is mostly not in the HTML as sent |
| `spf-missing` | DNS TXT of the domain | no `v=spf1` record |
| `dmarc-missing` | DNS TXT of `_dmarc.<domain>` | no `v=DMARC1` record |
| `link-broken` | the page's links, a bounded number, on the page's own site | a link answers 4xx or 5xx |
| `payment-methods` | the rendered page | information alone: the Gulf payment methods it shows (mada, Apple Pay, STC Pay, Tabby, Tamara) |
| `bot-challenge` | the page's answer | information: the site answers a named bot with a challenge (so AI crawlers may be refused too) |

The thresholds are the protocols' and the standards': "more than one redirect" is a chain; nothing counts as too
heavy or too slow without a number the owner or a standard sets. DNS lookups ask the resolver the scanner already
uses, for TXT records only. `link-broken` follows the site's own links only, one request each, within the scan's
budget, and says how many it did not check.

## 4. Risks

- **Rules that read DNS and follow links** widen what a scan does: both go through the egress package, within the
  scan's budget, and the SSRF suite gains cases for them.
- **The generators' output must be right in every browser:** each has unit tests of its output against the rule it
  names.
- **Copy:** fifteen more tools and fourteen rules, in both languages, for the owner to review.

## 5. M2.3a: the security headers and the redirects (the design as built)

Three pull requests, as the rules come: **M2.3a** the response's headers and the redirects; **M2.3b** the paste tool
and the generators; **M2.3c** the sitemap, DNS, links, the rendered text, payments and challenges.

**The header rules** read the final response's headers, as `hsts-missing` does, and apply to a 2xx HTML page on a
public host: like `https-missing`, they leave local development hosts alone, where no deployment's headers are set.
Rules that read headers need a collector of their own, `headers`, which `hsts-missing` and four others moved to, so the
example test can tell them from the rules that read the connection (`https-missing`, `tls-expiring`).

| Rule | Severity | Fails when |
| --- | --- | --- |
| `csp-missing` | minor | no `Content-Security-Policy` header and no `<meta http-equiv="Content-Security-Policy">` in `<head>`; a `Content-Security-Policy-Report-Only` one enforces nothing and does not count |
| `x-content-type-options-missing` | minor | no `X-Content-Type-Options` header whose value is `nosniff` (case aside, the first value, as browsers read it) |
| `frame-protection-missing` | minor | neither a `frame-ancestors` directive in an enforced CSP header (a `<meta>` CSP cannot set it) nor an `X-Frame-Options` of `DENY` or `SAMEORIGIN` |
| `referrer-policy-missing` | info | no `Referrer-Policy` header or `<meta name="referrer">`: browsers default to `strict-origin-when-cross-origin`, so it is said, never deducted |

**The redirect rules** read the redirects the page fetch followed (the report's `target.http.redirects`, now in the
rules' evidence as `redirects`):

| Rule | Severity | Fails when |
| --- | --- | --- |
| `redirect-chain` | minor | more than one redirect before the page |
| `redirect-temporary` | minor | a 302 or 307 that only changes the scheme to https, or the host between `example.com` and `www.example.com`, or both at once: moves that are permanent by nature |

**The tools:** `security-headers` (the four and `hsts-missing`), `tls-check` (`https-missing`, `tls-expiring`,
`hsts-missing`), `redirect-chain-check` (the two redirect rules). Their examples are HTTP exchanges, which the example
test checks against the rules as it checks HTML. Their cards, and the pages of their rules, say they read the
server's response, not the HTML.

**The fixture server** serves a site under several names, with routes for one name, so a wrong fixture can move
`shop.example` to `www.shop.example`; a redirect to one of its own names keeps the server's port.


## 6. Record (M2.3a)

**Built:** the four header rules, the two redirect rules and their three tools of §5. The engine passes the redirects
a page's fetch followed to the rules, the fixture server serves a site under several names, and tools can show an
HTTP exchange as their example, which the example test checks against the rules.

**The independent review** found, and the branch fixed:
- `redirect-chain` failed the chain the HSTS preload list requires (HTTP to HTTPS on the same host, then to the
  canonical name), and its fix broke preload. A first redirect that only moves the address to HTTPS on the same name
  is no longer counted, and the fix keeps that step.
- `redirect-temporary` left out `303`, which Google lists with `302` and `307`; a scan only sends GET. Its copy said
  Google takes a temporary redirect as no signal. Google calls it a weak signal, and a permanent one a strong signal.
- `frame-protection-missing` passed `frame-ancestors *`, which lets any site frame the page and makes browsers ignore
  `X-Frame-Options`. It now fails with a message of its own.
- Labelling a rule by its `headers` need called four HTML rules, and four HTML tools with them, readers of the
  server's response. `SERVER_RESPONSE_RULES` in the rules package now names the rules that judge the server's
  response; the site's labels and its self-audit both read it.

**Left as they are:**
- `csp-missing` counts any enforced policy, one that limits no scripts included, as its copy now says.
- When the HTML cannot be read in time, `csp-missing` and `referrer-policy-missing` report an error even where a
  header already settles them.
- The site itself passes the new rules: every page carries its policy in a `<meta>` with the hashes of its scripts
  and styles (M2.1), and the server sends `X-Frame-Options`, `X-Content-Type-Options` and `Referrer-Policy`.

**Checked (2026-09-29, the owner's Mac):**
- Every package's tests (the rules' 1035 among them) but the golden reports', which CI regenerates for the new
  rules and golden pages.
- The site's self-audit (186 pages) and the SEO self-audit.
- Lint, types and formatting.

## 7. Record (M2.3b)

**Built:** four tools that run in the visitor's browser, with nothing typed leaving it. The WhatsApp link generator
writes the link WhatsApp documents from a number typed as people type it: with `+` or `00`, spaces, a trunk 0, or
Eastern Arabic digits, and a full number typed without its `+` while a country is chosen. The hreflang generator
writes one set of tags for every version of a page. The product generator writes a Product with one Offer, the price
with its currency's own decimals. The robots.txt tester judges a pasted file for an address and a crawler, naming the
rule and its line. Each runs the code of the rule it names (`whatsapp-link-format`, `hreflang-invalid-code`,
`product-offer-invalid`, and the robots matcher), from `@arablyzer/generators`; their pages' examples are judged by
those rules like every tool's. A tool's definition says its kind, and the site's audit takes a paste or generator form
(`data-tool-kind`) with a real field in place of the address field.

**Waiting:** `arabic-slug-generator`. The generator is written (`arabicSlug`), but its page cannot show a live
example, because no rule judges a slug. It waits for a rule on URL slugs, or for a kind of page that needs none.

**Checked (2026-09-29, the owner's Mac):** the site's self-audit (176 pages); a browser suite in which each tool, in
Chromium, Firefox and WebKit, gives the answer its code gives in Node, the currency's decimals included, which each
browser reads from its own data; the site scanning its new pages; unit tests, lint, types and formatting.

**Found on the way:** the site's own scan took the WhatsApp generator's link-text field for a phone field, since its
placeholder names WhatsApp, and a phone field shown right to left reverses a typed number. The field holds text in
either language, so it takes its direction from what is typed (`dir="auto"`), as do the generators' other free-text
fields.
