# M4.7 PDF Export and White-Label — Implementation Plan

> **ملخص للمالك:** المعلم السابع من المرحلة 4: من سجّل الدخول يضغط «تنزيل PDF» على تقرير صفحة أو تقرير زحف أو مقارنة، فيصله ملف A4 مرتّب: غلاف فيه الموقع والتاريخ والدرجة، ثم الملخص، ثم المشكلات مجمّعة بحسب الخطورة مع خطوات الإصلاح، وصور «أشعة الحروف العربية» إن وُجدت. الملف عربي من اليمين إلى اليسار أو إنجليزي من اليسار إلى اليمين، بخطوط الموقع نفسها، ونصّه قابل للتحديد، وفيه ترقيم صفحات. يُرسم في متصفح الماسح (لا في الـAPI) عبر مهمة في الطابور، ملف واحد في وقت واحد لكل حساب، وبحدّ شهري للخطة (3 للمجاني). والـwhite-label (مغلق افتراضياً، مفتاحه في إعدادات الخطة): اسم شركتك وشعارها ولونها بدل علامة Arablyzer على الـPDF وعلى صفحة التقرير المشاركة، مع سطر «بواسطة Arablyzer» صغير يمكن للخطة حذفه. **المطلوب منك:** نصوص الواجهة والـPDF العربية (`reviewed: false`)، وقرار أي خطة تفتح white-label حين يأتي الدفع.

**Goal:** A signed-in person downloads a PDF of a page report, a crawl report or a comparison; an account whose plan has white-label puts its own name, colour and logo in place of Arablyzer's mark on the PDF and on its shared report page.

Design source: `docs/design/phase-4.md` (plans and limits; PDF and white-label were left to phase 5 there, and the owner moved them up). Built on `m4.2-sites.md` (account scans, history days), `m4.5-deep-crawl.md` (the API-image job process, the scanner's token, the lease) and `m4.6-compare-history.md` (comparisons, the pair checks).

## 0. Measured before planning (2026-10-10)

| Question | Result |
|---|---|
| Where can a PDF be drawn? | Only where Chromium is: the scanner image. Its browsers run a scanned site's code, so the scanner ends its process after any run that started one. A PDF of a report quotes a scanned site's words, so it is held the same way: it takes the scanner's one slot and the process restarts after it. |
| Print engine | Playwright 1.63's `page.pdf` (`tagged`, `outline`, CSS `@page` with margin boxes for page numbers: Chromium supports them). A golden report (Arabic, four pages) took 0.6 s and 160 KB, with IBM Plex Sans Arabic, DM Sans and IBM Plex Mono embedded as subsets. |
| How Chromium writes Arabic | Glyphs in drawn (left-to-right) order, wrapped in `/ReversedChars`, each with the base letter in `/ActualText`; the font's ToUnicode gives presentation forms. A PDF reader that honours these (Adobe) copies logical text. **pdf.js does not**: it reads the drawn order and the presentation forms. The browser test therefore normalises (NFKC) and reads a purely Arabic line from its far end, and compares words by their ends, since two letters that share a position come out in either order. The outline's Arabic titles come back in pdf.js's own word order and are not compared. |
| Fonts | Fontsource files the site is built with (`@fontsource/*`, woff2), inlined into the page as `data:` URLs; the browser has no system font to fall back on that a layout could depend on. |
| Where the report lives | `scans.report` (a scan) and `crawl*` rows (a crawl's report is computed on read: `reportOf`); a comparison is computed on read (`compareScans`, `compareCrawls`). The PDF job reads them as they are when it runs. |
| Rule fix text | `rule.copy[lang].sections.fix`: a small Markdown (lists, fenced code, code spans, the odd table). Read by a 60-line reader, not a Markdown library. |

## Global Constraints

- Invisible and 404 with `ARABLYZER_ACCOUNTS` off; the `pdf` process idles with it off. Anonymous scans, tools and reports unchanged (the report page asks for a brand and an account only when the build has a Google client id).
- **Never in the API process.** The route queues (`pdf_jobs`); the `pdf` process (API image, application role) builds the document and asks the scanner (`POST /pdf`, the worker's token); the scanner draws it. The document is JSON of capped plain-text fields (`packages/pdf/src/model.ts`), checked against a Zod schema where the scanner receives it, never markup: every string is escaped (and tested with hostile input), the page is served under `default-src 'none'; style-src 'unsafe-inline'; font-src data:; img-src data:`, every request but the document's is refused, the browser's proxy is a closed port, and its environment has none of the process's secrets.
- **Caps.** 8 MB and 60 s a PDF (the scanner stops at 75 s); a document of at most 6 MB (pictures drop first); at most 40 sections, 500 blocks each; 150 findings or changes a section.
- **One at a time per account**, held by the database (partial unique index on active PDFs). **Monthly cap** `ARABLYZER_PLAN_ACCOUNT_PDF_PER_MONTH` (default 3, also in production), counted in a ledger (`pdf_usage`), checked and incremented in one statement with the insert; a PDF that fails is given back.
- **Kept as long as the report**: `pdf_jobs.scan_id`/`crawl_id` are foreign keys with cascade (a comparison's is its later report), so whatever deletes a report deletes the file; and no longer than the plan's history days (the job process expires files, then deletes rows after `max(days, 35)`). Deleted with the account (cascade, and `eraseUser`, tested).
- **White-label** is a plan capability (`ARABLYZER_PLAN_ACCOUNT_WHITE_LABEL`, default off; `…_WHITE_LABEL_CREDIT`, default on, takes the "by Arablyzer" line away), config-only until M4.4. Name ≤ 60 characters, control characters removed; colour `#rrggbb`, used only if white text on it reaches 4.5:1 (else Arablyzer's own, and the form says so); logo PNG/JPEG/WebP by magic bytes (never by type or name; SVG is refused), ≤ 200 KB and 2048 px a side, metadata chunks/segments removed, stored in PostgreSQL (`account_brand`), erased with the account, served with `nosniff` and a `sandbox` policy.
- **The shared report page** shows the brand of the account that keeps the scan (`GET /api/reports/:id/brand`, public, name/colour/logo only, 404 for a scan no account keeps or a plan without white-label). It is a bar above the report; the site's header stays.
- UI on the R7 scale; no `style=` in markup: the brand colour is set on the element through the style object (`el.style.setProperty('--brand', …)`, which the page's policy does not restrict, and the browser test runs under the built page's own policy). Every new Arabic string is `reviewed: false`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **The scanner takes a document, not markup**; hostile text lands as text in every field. Task 3.
2. **No network from the PDF page**: the browser test serves a local port and asserts it was never asked. Task 3.
3. **Limits are the database's**: two requests at once make one PDF; the month's cap is not passed by a race; a failed PDF is given back. Tasks 2, 5.
4. **Not someone else's**: a report, PDF or brand of another person is a 404; a shared report shows a brand only while the plan has white-label. Task 5.
5. **Logo by bytes**: SVG, oversize, huge dimensions and a picture under a false type. Task 4.

## Tasks

1. Plan numbers, contract, i18n. 2. Store and migration (memory + PostgreSQL contract). 3. The document, the HTML, the browser's `renderPdf`, the scanner's route and client; the Chromium test. 4. Logo check and colour guard. 5. API routes, the job and its process, erasure. 6. UI. 7. Infra, checks, CI, the record.

## Acceptance criteria

1. Flag on: a PDF of a page report, a crawl report and a comparison, in Arabic and in English, is made by the `pdf` process through the scanner; one at a time, within the month; kept with the report; gone with the account. A plan with white-label shows its brand on the PDF and the shared report page; one without shows Arablyzer's.
2. Flag off: every route is 404, nothing is linked or asked for.
3. `pnpm lint`, `format:check`, `typecheck`, unit tests, web build, `site:audit` pass.

## Not in M4.7

Charts in the PDF, a PDF of the score history, PDFs of an anonymous report, a custom domain or e-mail sender for white-label, a brand per client (agency spaces, phase 5), re-encoding the logo (metadata is removed, the picture is kept as it is), a download from the shared report page for someone not signed in.

## For the owner

1. The Arabic of the PDF and of the form and buttons (`reviewed: false`).
2. Which plan opens white-label, and whether it removes the «by Arablyzer» line, when payments exist (M4.4).
3. Chromium writes Arabic in drawn order with the letters in `/ActualText`: Adobe-class readers copy it correctly; pdf.js and some previewers copy it in visual order. If that matters, the fix is a post-processing step, a separate decision.
