# M5.1 Public API, OpenAPI and the MCP Server — Implementation Plan

> **ملخص للمالك:** أول نصفَي المرحلة 5: من سجّل الدخول ينشئ حتى مفتاحين للـ API من `/account` (يُعرض السر مرة واحدة ولا نحتفظ إلا ببصمته، ويُلغى بزر)، ويستعملهما بـ `Authorization: Bearer arb_…` على `/api/v1/`: يبدأ فحصاً، يسأل عن حالته، يقرأ التقرير (نفس مخطط التقرير الحالي)، يعدّد الأدوات والقواعد، ويشغّل أداة واحدة. كل ذلك من حصة الحساب نفسها (دلو واحد لا حصة ثانية)، وله مواصفة OpenAPI 3.1 على `/api/v1/openapi.json` وصفحة `/developers` بالعربية والإنجليزية. وخادم MCP (stdio وHTTP على `/mcp`) يتيح لمساعد ذكي أن يفحص صفحة ويقرأ تقريرها. كله مطفأ مع `ARABLYZER_ACCOUNTS` (الـ API يردّ `503 accounts_off`). **المطلوب منك:** نصوص الواجهة العربية (`reviewed: false`) وأرقام حصة الـ API إن أردت غير الافتراضي.

**Goal:** A signed-in account makes API keys and drives scans, reports, tools and rules over a stable, documented HTTP API, and an AI assistant does the same through MCP, all inside the account's existing quota.

Design source: `docs/design/phase-4.md` (plans, quotas, erasure), `m4.1-accounts.md` (sessions), `m4.2-sites.md` (account scans).

## 0. Measured before planning (2026-10-11)

| Question | Result |
|---|---|
| Is there a report cache to reuse for idempotency? | No. A repeat scan is a new scan today. "Same URL within the window returns the earlier scan" is built here on the account's own history (`history` + `linkedScans`): same canonical URL, source `manual`, not failed, made in the last 10 minutes. |
| What does a quota need to say? | The limiter returned only ok/not. It gains an optional `remaining()` (read apart from `take`, so existing results are untouched), so responses carry honest headers. |
| Can a scan choose engines? | No: `ARABLYZER_ENGINES` is the scanner's, per deployment. A per-scan subset is plumbed worker → scanner (intersected with what the scanner runs). A subset scan is a one-off: not linked to the account's history, not reusable, so scores in history stay comparable. |
| Is the rule library reachable from the API? | The API process already loads `@arablyzer/rules` (copy files included); `GET /api/v1/rules` reads it. |
| MCP SDK | `@modelcontextprotocol/sdk` 1.32.1 (pinned), `zod ^3.25 \|\| ^4`, a web-standard streamable HTTP transport (Request → Response) that fits Hono. |

## Global Constraints

- **Off with accounts off**: the key routes are 404 and the account page hides the panel; every `/api/v1/*` route (not the spec) answers `503 {error:{code:'accounts_off'}}`; `/mcp` the same. The spec at `/api/v1/openapi.json` is documentation and is always served.
- **Auth** is `Authorization: Bearer arb_<43 chars>` only; a session cookie never authenticates v1 (so no CSRF surface, and no Origin check is asked of a bearer client). A bad, revoked or missing key is one answer, `401`, with `WWW-Authenticate: Bearer`.
- **Keys**: 256 random bits; shown once at creation; kept as SHA-256 only (the delete-token precedent, `ids.ts`: a hash of 256 random bits needs no salt and no stretching, and a slow hash would make every request a CPU cost); a prefix (`arb_` + 4 characters) is kept to tell keys apart. At most `apiKeys` (default 2) per account; revoked keys do not count and stay out of lists. Erased with the account (FK cascade plus `eraseUser`).
- **One bucket**: a v1 scan takes a token from the account's bucket (`account:<id>`) exactly as a scan from the site does. `ARABLYZER_PLAN_<PLAN>_API_SCANS` unset = the API shares the whole bucket; a number N = the API may use at most N of the window's scans (a cap inside the bucket, never a second allowance); `0` = no API for the plan (`403 plan_limit`). Reads cost no scan token but count against a per-key request budget (`API_REQUESTS` per minute, default 120).
- **Egress and limits are untouched**: v1 starts scans through the same `startScan` (parse, DNS vetting, per-host limit, in-flight places, queue cap, the address throttle). A reused scan consumes nothing.
- **Never breaks the internal routes**; only additions (`startScan` gains an optional fourth argument; `RateLimiter` gains an optional `remaining()`).
- **Reads by id**: a scan's state and report are read by their id with any valid key, as the report page is read by anyone with the id today (128 random bits); the account's own list is `GET /scans`. A visitor who keeps presenting keys nobody holds is stopped by address (the attempts window), before the store is asked.
- **Envelope**: `{data}`; lists `{data:[…], meta:{nextCursor}}`; errors `{error:{code,message,details?}}` with a stable snake_case code. `RateLimit-Limit/Remaining/Reset` on every v1 answer (the request budget); scan starts add `X-Scans-Limit`, `X-Scans-Remaining` (the account bucket). `Cache-Control: no-store`.
- **MCP calls the API, never the engine**: the HTTP endpoint hands the MCP server a client whose `fetch` is the API's own `app.fetch` with the caller's key; stdio uses the same client over the network with `ARABLYZER_API_KEY` and `ARABLYZER_API_URL`. Tool results are capped (findings summary, not the whole report).
- UI on the R7 scale; no `style=` (CSP); every new Arabic string `reviewed: false`. Commits end with `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`.

## Review Focus

1. **One bucket**: a cap of N never lets the API exceed the account bucket, and a reused scan costs nothing. Task 5.
2. **A key proves only itself**: hash lookup, revoked = 401, a cookie alone = 401, another account's key cannot be revoked (404). Tasks 3, 4.
3. **Spec equals routes**: a test lists the Hono app's `/api/v1` routes and the spec's paths both ways and parses real responses against the spec's schemas. Task 6.
4. **Erasure**: keys gone with the account. Task 3.

## 2. Contracts

| Route | Success | Refusals |
|---|---|---|
| `POST /api/v1/scans` `{url, engines?}` | 202 `Scan` + `deleteToken`; 200 `Scan` with `reused:true` | 400 `invalid_request`/`invalid_url`, 401, 403 `plan_limit`, 422 `blocked_target`, 429, 503 |
| `GET /api/v1/scans?limit&cursor` | `Scan[]`, newest first, the account's | 400, 401 |
| `GET /api/v1/scans/{id}` | `Scan` | 401, 404 |
| `GET /api/v1/scans/{id}/report` | the report (existing schema) | 401, 404, 409 `report_not_ready` |
| `GET /api/v1/tools?limit&cursor` | `Tool[]` | 400, 401 |
| `POST /api/v1/tools/{slug}/runs` `{url}` | 202 `Scan` (a tool's scan; read it with the scan routes) | as scans, 404 unknown tool |
| `GET /api/v1/rules?limit&cursor`, `GET /api/v1/rules/{id}` | `Rule[]`, `RuleDetail` (AR/EN) | 404 |
| `GET /api/v1/openapi.json` | OpenAPI 3.1 | none |
| `GET /api/account/keys`, `POST`, `DELETE /:id` | `{keys, limit}`, 201 `{key, secret}`, 204 | 401, 403 `plan-limit apiKeys`, 404 |
| `POST /mcp` | MCP (stateless streamable HTTP, JSON responses) | 401, 503 |

Deleting a v1 scan uses the existing `DELETE /api/reports/:id` with the `deleteToken` of the creation answer.

## 3. Tasks

1. Contract, plans, limiter `remaining`, engines plumbing (unit tests).
2. Store: `ApiKeyData`, migration `0008`, contract test run on memory and (CI) PostgreSQL; erasure.
3. API: key routes; v1 auth, routes, idempotency, presenters; config/dev/server wiring; tests (keys, auth, quota, reuse, envelope, headers, spec coverage).
4. `packages/mcp`: client, summary, server, stdio, HTTP; tests with an in-memory MCP transport and a mocked client; `/mcp` mount test.
5. Web: panel, `/developers`, footer, sitemap, Caddy `/mcp`; unit tests of the panel's model.
6. `docs/mcp.md`; checks; PR; CI.
