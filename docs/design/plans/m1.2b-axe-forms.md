## 0. Measured before planning (2026-09-27, the owner's Mac)

Chromium 153 and Firefox 155, axe-core 4.13.0, on right-to-left Arabic test pages set with `page.setContent`:

| Question | Result |
|---|---|
| The curated rules on Arabic content | `image-alt`, `link-name`, `button-name`, `valid-lang` and `label` found every planted case in both engines, and nothing else; two runs gave the same results; 36–124 ms a run |
| `color-contrast` on Arabic text | **Not checked at all.** axe's `isIconLigature` takes Arabic sentences for icon-font ligatures: it draws the first character alone at the left edge and compares it with the whole text, and an Arabic sentence's first letter sits at the right, joined. After three such text nodes in one font family, axe skips every text node in that font, English included. A page with three dark Arabic paragraphs and a light grey Arabic and English one: 0 violations, 0 passes, in both engines |
| Telling axe that the fonts of Arabic text are not icon fonts | Seeding axe's font cache (`axe._cache`, key `fonts`) with those families as seen and never a ligature, before `axe.run`: both light paragraphs fail, text over an image is incomplete (`bgImage`), the dark ones pass, in both engines. Icon fonts, whose ligatures are Latin names such as `shopping_cart`, keep axe's check |
| A phone number in right-to-left text | «+968 9123 4567» shows as «4567 9123 968+»; `dir="ltr"`, `dir="auto"` and `unicode-bidi: plaintext` show it in order |
| Phone inputs on right-to-left pages | Both engines give `<input type="tel">` direction `ltr`; `type="text"` stays `rtl`, with `inputmode="tel"` or `autocomplete="tel"` too. WebKit is measured in CI |

## 1. Rules

| Rule | Category · severity | Fails when | From |
|---|---|---|---|
| `a11y-image-alt` | trust · critical | An image has no text alternative | axe `image-alt` |
| `a11y-color-contrast` | trust · serious | Text, Arabic included, is below WCAG 1.4.3's contrast (4.5:1, 3:1 for large text) | axe `color-contrast`, with the font cache seeded |
| `a11y-color-contrast-review` | trust · serious, needs review | axe could not measure a text's contrast, such as text over an image | axe `color-contrast`, incomplete |
| `a11y-link-name` | trust · serious | A link has no accessible name | axe `link-name` |
| `a11y-button-name` | trust · critical | A button has no accessible name | axe `button-name` |
| `a11y-valid-lang` | trust · serious | A `lang` attribute inside the page is not a valid language | axe `valid-lang` |
| `form-label-missing` | forms · critical | A form field has no label | axe `label` |
| `form-phone-direction` | forms · moderate | A phone field shows right to left, so a typed number shows reversed | computed style |

The accessibility rules are in the `trust` category, where BUILD-PLAN §4 puts `accessibility-check`: the rule model (§10) has no accessibility category. Severities follow axe's own impact for its rules. `form-phone-direction` is moderate: the number is stored right,
only shown reversed while typing.

## 2. How the rules decide

- **axe runs once per engine**, after the page is measured, on the curated rules only, in the page's own world as
  the measuring script does (a page can falsify its own results, and only its own). Results are validated and
  bounded in Node: at most 20 nodes a rule, each with its selector and the first 200 characters of its HTML.
- **Violations fail the rule; axe's "incomplete" makes it "needs review"**, with the reason axe gives
  (`bgImage`, `bgGradient`, `bgOverlap`…), as the Phase 1 design asks where we cannot be sure.
- **Contrast of Arabic text:** before `axe.run`, the families of elements whose own text has Arabic letters are
  seeded in axe's font cache as not icon fonts. The seed rests on axe's internals, so axe-core is pinned, and the
  fixtures fail if an update changes this.
- **Phone fields:** the rendered page reports, for each input, its type, name, id, autocomplete, inputmode,
  placeholder, label, `dir` attribute and computed `direction` and `unicode-bidi`. A phone field (autocomplete
  `tel*`, `inputmode="tel"`, or a name, id, label or placeholder that names a phone, «هاتف»، «جوال», `phone`,
  `mobile`…) fails when its direction is `rtl` and neither `dir="auto"` nor `unicode-bidi: plaintext` reorders it.
- **Overlaps:** axe's `html-has-lang`, `html-lang-valid` and `document-title` stay out: `ar-html-lang` and
  `title-missing` cover them.

## 3. Facts (`collectors`, `browser`)

- `RenderedFacts.a11y`: per curated axe rule, its violations and incomplete nodes (selector, snippet, and the
  check's message key), or null when axe did not run.
- `RenderedFacts.fields`: inputs, textareas and selects with the attributes above and their computed direction.
- axe's source ships with the browser package and the CLI bundle, read once per process.

## 4. Tests

- Each rule: wrong and right fixtures rendered in every available engine by the engine's browser suite, a detector
  test on facts, Arabic and English copy.
- Contrast: a fixture with three Arabic paragraphs before a low-contrast one, which axe alone would skip.
- Browser package: axe's results on a page with one case per rule, in each engine; the seed; bounds.

## 5. Commits

Plan → browser facts (axe, fields) → one commit per rule → README and record.

**Changes from the plan, and why**

- **Eight rules, not seven.** Contrast is two: `a11y-color-contrast` fails where axe is sure, and
  `a11y-color-contrast-review` (`manualCheck`) asks for a look where axe cannot measure, such as text over an
  image. A rule's status is one for the page, and "needs review" is never deducted, so the two could not share a
  rule. The render matrix now expects such a rule's wrong fixture to need review and its right one not to apply.
- **The accessibility rules are in the `trust` category**, where BUILD-PLAN §4 puts `accessibility-check`; the rule
  model of §10 has no accessibility category, and the schema keeps its list.
- **axe says which rules had nothing to check** (`applicable`), so a page without images has no
  `a11y-image-alt` result rather than a pass.
- **What page scripts hand to Node goes through a guard** (review finding 1, below), M1.1's measuring script
  included.

## Review (2026-09-27)

An independent review ran hostile pages in Chromium and Firefox and checked the copy against axe-core 4.13.0 and
WCAG 2.2. It confirmed that a page cannot hold the render past axe's 10 s, that an axe failure costs the page
only its `a11y` facts, and that the font-cache seed does what it says and leaves real icon fonts to axe. Each
finding was reproduced before its fix.

| # | Finding | Fix |
|---|---|---|
| 1 | Our page scripts run in the page's world, where the page can replace any built-in; by standing in for `window.axe`, or replacing `String.prototype.slice`, a page could make a result of hundreds of megabytes reach Node before validation refused it. The same held for M1.1's measuring script | An init script, run before the page's own, keeps `JSON.stringify` and defines a non-writable, non-configurable `window.__arablyzerResult`; every script result crosses through it, as text of at most 2,000,000 characters. A page that poisons `slice` fails its render with "over the limit"; one that stands in for axe keeps its other facts |
| 2 | `form-phone-direction` matched phone words inside other words: «iPhone», «Headphone», «automobile», «جوالات» in a search box | Labels and placeholders are read word by word, Arabic words with their clitics but not plurals; search boxes and message fields are left out |
| 3 | `a11y-button-name`'s copy claimed `<input type="button">`, which is axe's `input-button-name` | The copy says it is another axe rule |
| 4 | `form-label-missing`'s copy claimed `<select>`, which is axe's `select-name` | The copy says so |

**For later:** axe's `input-button-name` and `select-name` would cover the two gaps above; each needs its own
rule, fixtures and copy.
