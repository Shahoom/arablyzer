# M4.3 Monitoring — Implementation Plan

> **ملخص للمالك:** المعلم الثالث من المرحلة 4: من سجّل الدخول يفعّل «المراقبة» على موقع محفوظ، فيُفحص وحده كل 7 أيام (للخطة المجانية: موقع واحد)، ويصله تنبيه على رابط webhook يلصقه في `/account` (Slack وDiscord وJSON عام، موقّع بـHMAC، يمرّ عبر وكيل الخروج) عند: هبوط الدرجة أكثر من حد يختاره، أو مشكلة حرجة جديدة، أو تعذّر فحص الموقع، أو ملخص أسبوعي اختياري. البريد خلف واجهة مطفأة حتى يوجد Resend (`ARABLYZER_MAIL_PROVIDER` غير مضبوط = مطفأ)؛ لا واتساب. المجدول عملية مستقلة (خدمة `monitor` في Compose) لا داخل العامل: دور العامل في قاعدة البيانات لا يقرأ الحسابات ولا ينشئ فحوصاً بقرار M4.1، فبقي كذلك. كل شيء مطفأ بعلم `ARABLYZER_ACCOUNTS`. **ينتظرك:** أرقام الخطة المجانية الموصى بها (مكتوبة في `.env.example` ودليل التشغيل)، وقراءة النص العربي الجديد (`reviewed: false`).

**Goal:** A signed-in person turns monitoring on for a saved site; it is scanned on the plan's schedule without them, and a webhook tells them when the score drops, a new critical finding appears, or the site cannot be scanned.

Design source: `docs/design/phase-4.md` §2.2 (`monitors`, `monitor_runs`), §2.3 (`monitoredSites`, `monitorEveryDays`). Built on `m4.2-sites.md`.

## 0. Measured before planning (2026-10-09)

| Question | Result |
|---|---|
| Where the scheduler runs | The worker's database role (`arablyzer_worker`) reads and updates scans only: it cannot insert one nor read an account (M4.1, so what takes it over reaches no account). Scheduling needs both. So the scheduler is a second entry of `apps/api` (`src/monitor/main.ts`), one more Compose service on the API image and the app role, with no port. The scan worker is unchanged |
| Starting a scan | `startScan` is bound to a request. The scheduler repeats its steps that matter without a visitor: place under `account:<id>` with the plan's `inFlight`, DNS vetting (`resolveTarget`), the per-host bucket, the queue cap, then store → link → event → queue (same order, same failure handling) |
| Outbound calls | `safeFetch` with a JSON body, extra headers and `ARABLYZER_EGRESS_PROXY`, as the Search Console calls do; never redirected; 64 KB cap. The signature covers the exact bytes `safeFetch` sends (`JSON.stringify` of the payload) |
| What survives retention | `monitor_runs.scan_id` is a foreign key to `scans` with cascade: the history sweep that deletes a scan deletes its run, so runs live exactly as long as the plan's history days |
| Free-plan numbers | Owner, 2026-10: 5 scans a day, 1 at a time, 3 saved sites, history 5 days, monitoring weekly for 1 site. Written as the recommended values in `infra/.env.example` and `infra/README.md`; the code keeps no default for the first five in production |

## Global Constraints

- Invisible and 404 with `ARABLYZER_ACCOUNTS` off; the scheduler process refuses to start with it off.
- `monitoredSites` and `monitorEveryDays` are checked at `PUT /api/sites/:id/monitor` **and on every run**; a downgrade pauses the extra monitors (the oldest are kept), and the interval never goes below the plan's.
- A monitor scan is never ahead of a visitor: it starts only while the queue holds fewer than half of its cap, takes the per-host bucket, and holds the account's place (so a person's own scan in flight defers it). It takes none of the account's manual scan bucket and none of the visitor buckets.
- Idempotent: the claim is `FOR UPDATE SKIP LOCKED` with a lease, and `(monitor, scheduled_for)` is unique, so two schedulers or a restart never make two runs for one slot. Jitter on the first run and on each next date.
- The webhook URL and secret are never returned after saving (host only); the secret is shown once. Requests are `https` only, vetted by the egress policy at save and again at send.
- Alerts are decided from the scan store (current and previous report), not from anything the scheduler remembers.
- UI on the R7 scale, no `style=`, AR+EN copy `reviewed: false`. Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Two enables at the limit** store one (transaction + per-user advisory lock). Task 2.
2. **Downgrade**: a plan with fewer monitored sites pauses extras at the next run and raises the interval. Task 5.
3. **Scheduler under load**: queue past half, host bucket empty, person's place held: the run is deferred with backoff, nothing is started, no slot is lost or doubled. Task 5.
4. **Alerts fire once per run**; a failing webhook is retried with backoff (1 min, 5 min, 30 min, 2 h, 6 h), then dropped, and 5 failures in a row disable it. Task 6.
5. **Erasure** leaves nothing in the new tables (existing all-tables search). Task 3.

## 2. Contracts

| Route | Guards | Success | Refusals |
|---|---|---|---|
| `PUT /api/sites/:id/monitor {enabled}` | Origin, JSON, session | 200 `MonitorSummary` or `{monitor: null}` | 401, 404, 403 `plan-limit` (`monitoredSites`) |
| `GET /api/sites` | | `SiteSummary.monitor` and `monitoring: {limit, everyDays}` added | |
| `GET /api/account/alerts` | session | `AlertSettings` (webhook as host and kind only) | 401 |
| `PUT /api/account/alerts` | Origin, JSON, session | `AlertSettings` + `secret` once, when a URL was set or rotated | 400, 401, 422 (URL refused) |
| `POST /api/account/alerts/test` | Origin, session | `{ok, status}` (also re-enables a disabled webhook that answers) | 400 (none saved), 429 |

Payloads: Slack `{text}`, Discord `{content}`, generic `{type, version: 1, site, scan, previous, events, at}`. Headers `X-Arablyzer-Timestamp` and `X-Arablyzer-Signature: sha256=<HMAC of "<timestamp>.<body>">`.

**Settings:** `ARABLYZER_PLAN_ACCOUNT_MONITORED_SITES` (default 1), `ARABLYZER_PLAN_ACCOUNT_MONITOR_EVERY_DAYS` (default 7), `ARABLYZER_MAIL_PROVIDER` (unset = off; any other value refuses to start until a provider is built). Paid plans read the same names with their prefix.

## Tasks

1. **Plan numbers and contract** — fields, defaults, tests; shapes and Zod.
2. **Tables and `MonitorData`** — enable under lock, disable, claim with lease, record run (account link + run + next date in one transaction), defer, pause extras, pending runs, previous scan, trend, alert settings, delivery bookkeeping. Shared contract suite over memory and PostgreSQL.
3. **Erasure** — `eraseUser` extended; the all-tables search finds nothing.
4. **Routes** — monitor toggle and alert settings, test button with its own limiter key.
5. **Scheduler** — tick: pause extras, claim, start or defer. Jitter, caps, backoff. Tests with a fake clock.
6. **Alerts** — evaluate (drop ≥ threshold, new critical fingerprints, failed or unreachable), weekly summary opt-in (at most every 7 days), delivery with retries, auto-disable, mail interface (off).
7. **The page** — `MonitorPanel` inside each site row and a webhook card.
8. **Settings, CI, the record.**

## Acceptance criteria

1. With the flag on: enabling monitoring at the limit is `403 plan-limit`; the scheduler starts due runs, never beyond the queue half or a person's place; a drop, a new critical finding or a failed scan sends one signed webhook; the test button works; erasing the account leaves nothing.
2. Flag off: every route 404 and the monitor process refuses to start. Anonymous scans, tools and reports unchanged.
3. `pnpm lint`, `format:check`, `typecheck`, unit and service tests, web build, `site:audit` pass.

## Not in M4.3

Email delivery (interface only), WhatsApp, per-site thresholds, choosing the interval on the free plan, subscriptions and plan changes (M4.4), re-alerting on recovery.

## For the owner

1. Set the recommended free-plan numbers in the deployment (`infra/README.md`): 5 scans a day, 1 at a time, 3 saved sites, history 5 days, monitoring 1 site every 7 days.
2. The Arabic of the monitoring card, the webhook form and the alert messages (`reviewed: false`).
3. Resend later: one `Mailer` implementation and `ARABLYZER_MAIL_PROVIDER`.
